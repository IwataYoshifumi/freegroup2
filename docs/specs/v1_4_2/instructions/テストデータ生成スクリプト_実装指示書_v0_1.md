## 2. 実装範囲

### 2.1 ファイル名・配置・実行方法

| 項目 | 内容 |
|---|---|
| ファイル名 | `dev_create_test_contact_data.py` |
| 配置 | `cards/management/commands/` |
| 実行方法 | `python manage.py dev_create_test_contact_data [options]` |
| 命名規則 | `dev_*` プレフィックス（開発用管理コマンド、§13.5 別表B 参照） |

### 2.2 専用ユーザー

専用テストユーザー `test_data_user` を Django Admin で事前作成しておく前提（パスワード・権限はたんたんが任意設定）。スクリプトは取得のみで作成は行わない。

- 起動時に `User.objects.get(username='test_data_user')` で取得
- 存在しなければエラー終了し、Admin での作成を促すメッセージを表示
- 生成する Contact / Person / ContactFieldConfidence の `created_by` / `updated_by` は `test_data_user` に統一
- `--reset` 時は `test_data_user` が `created_by` の Contact / Person / ContactFieldConfidence / DuplicateCandidate / PersonMergeLog / ActionLog を全削除

### 2.3 生成するモデル

| モデル | 生成有無 | 備考 |
|---|---|---|
| Person | ✅ 生成 | `status='active'` |
| Contact | ✅ 生成 | `status='primary'`、`business_card=None`、`created_by=test_data_user` |
| ContactFieldConfidence | ✅ 生成 | `--confidence-mode` に応じて low/medium レコードを作成 |
| BusinessCard | ❌ 作らない | テストデータでは OCR 経路を再現しない |
| OriginalImage | ❌ 作らない | 同上 |
| DuplicateCandidate | ❌ 作らない | cron 起動 → 自動生成を確認するためのテストデータ |
| PersonMergeLog | ❌ 作らない | C ブロック実装後の検証で生成される |

### 2.4 セットデータ7プール

#### プール1：氏名

姓 30件程度（山田 / 田中 / 鈴木 …）、男性名・女性名 各20件程度をプール化。グループ④（同姓同名）用に「同じ氏名」を意図的に複数回使えるようにする。

ローマ字変換は不要（メールアドレス生成のため別途ローマ字プールを持つ、またはローマ字変換ロジックを最小限実装する。実装方針はコード君A に委ねる）。

#### プール2：会社プール（最重要、構造化必須）

会社単位で以下を1セットとして保持：

- 会社名（前株 / 後株 / 有限会社 / 合同会社 / 表記なし のバリエーション）
- ドメイン
- 本社代表電話 / 本社代表 FAX
- 代表メール（§8.7 / §14.3.6 の DUPLICATE_GENERIC_EMAIL_LOCALPARTS から `info@` / `support@` / `sales@` などを使う）
- 本社住所（郵便番号 + 住所）
- 拠点プール（複数）：拠点名（例：東京営業所）/ 拠点電話 / 拠点 FAX / 拠点住所

会社規模の目安：8〜15社程度。各社に拠点 2〜3 ヶ所。前株と後株を意図的に混ぜる（§15.5.3 の「前株/後株は別会社扱い」を踏まえた現実的な揺れ）。

#### プール3：部署

営業系 / 技術系 / 管理系 / 製造系 / その他の 5 カテゴリ計 25〜35 件。

- 営業系：営業部、営業1課、首都圏営業部、関西営業所 など
- 技術系：技術部、開発部、研究開発部 など
- 管理系：総務部、人事部、経理部、IT 推進部 など
- 製造系：製造部、製造1課、生産管理部、品質管理部
- その他：企画部、経営企画室、社長室、購買部、物流部

#### プール4：役職

階層別に 5〜7 段階：

- 平社員系：（空欄）/ メンバー / 担当
- 主任系：主任 / 係長 / リーダー / チーフ
- 課長系：課長 / 課長代理 / マネージャー / グループ長
- 部長系：部長 / 部長代理 / シニアマネージャー / 本部長 / 室長
- 役員系：執行役員 / 取締役 / 常務取締役 / 専務取締役 / 副社長 / 代表取締役 / 社長

#### プール5：メールアドレス

個人用パターンと共用パターンを分離：

- **個人用パターン**：`{romaji_first}.{romaji_last}@` / `{romaji_first_initial}.{romaji_last}@` / `{romaji_last}{number}@` / `{romaji_full}@`
- **共用パターン（§14.3.6 と整合）**：`info@` / `contact@` / `support@` / `sales@` / `admin@` / `office@` / `mail@` / `inquiry@` / `help@` / `service@` / `shop@` / `customer@` / `reception@`
- **バリエーション（§8.7）**：ハイフン・アンダースコア・ドット付き（`info-jp@` / `sales_team@` / `support.tokyo@` など）
- **ドメイン**：会社専用ドメイン（プール2 の会社ごと）/ フリーメール（gmail.com / yahoo.co.jp / outlook.com）

#### プール6：電話番号

DB には数字のみで保存される（§15.5.3）ため、プールの値は最初から数字のみで持つ。

- **携帯**：`090XXXXXXXX` / `080XXXXXXXX` / `070XXXXXXXX`
- **固定電話**：`03XXXXXXXX`（東京）/ `052XXXXXXX`（名古屋）/ `0565XXXXXX`（豊田）/ `06XXXXXXXX`（大阪）/ `011XXXXXXX`（札幌）など
- **会社代表 / FAX**：会社単位で固定（プール2 で1セット保持）

#### プール7：住所

都道府県・市区町村プール 10〜15 件 × 番地・ビル名パターン。会社単位で本社住所・拠点住所を固定保持（プール2 と連動）。

### 2.5 部署違いとイレギュラーパターン

- 同じ会社・部署なら基本同じ電話番号・FAX・住所を使う
- 拠点系部署（営業所・支店等）は拠点プールの値を使う
- 本社系部署（総務部・経理部等）は本社の値を使う
- **イレギュラーパターン**を `--irregular-rate`（デフォルト 0.1 = 10%）の確率で混ぜる：
  - 同じ会社・部署でも電話番号違う
  - 住所やメールアドレスが違う
  - 郵便番号と住所が古い情報のまま、など

### 2.6 グループ別生成ロジック

#### グループ① 完全同一名刺（デフォルト 5 人、`--clone N`）

「山田太郎」さんの同じ名刺を複数枚スキャンしたケース。OCR を複数回通すと別 Person・別 Contact として登録される想定。

- 全フィールド一致：`full_name` / `email` / `mobile` / `company` / `department` / `title` 全部同じ
- 期待：cron 後、全ペアが `exact_match` で pending DC、`group_id` は全部同じ G1 にまとまる
- DC 期待件数：N=5 で最大 10 件（5C2 = 10）

#### グループ② 異動・転職（デフォルト 4 人、`--career N`）

「鈴木花子」さんが異動・転職・出向で会社や部署が変わった。OCR で取り込むたびに別 Contact / 別 Person として登録。4 パターンを順に当てる：

- パターンA：同一会社内の異動（部署 or 役職が変わる、メール命名規則は維持）
- パターンB：同一会社内の昇進（役職のみ変わる）
- パターンC：転職（会社・部署・メール・固定電話が変わる、携帯は維持）
- パターンD：出向（会社・部署が変わる、携帯も変わる、フルネームは維持）

期待：ランクの段階を全部試せる。スコア計算ロジックの確認に最重要。
DC 期待件数：N=4 で最大 6 件（4C2 = 6）。

N≠4 の場合の振り分けロジックはコード君A に委ねる（A→B→C→D を循環させる方針が自然）。

#### グループ③ 改姓・部署変更（デフォルト 3 人、`--namechange N`）

「田中由美」さんが結婚して「佐藤由美」になった。同時に部署異動もあり。3 バリエーション：

- 姓だけ変わる、部署も会社も維持（メール命名規則は変わる）
- 姓 + 部署変更
- 姓 + 会社変更（離婚＋転職など）

期待：「フルネーム不一致でも携帯一致で possible_high の閾値（200点）に届くか」をテスト。§8.4 の確認。
DC 期待件数：N=3 で最大 3 件（3C2 = 3）。

#### グループ④ 同姓同名（デフォルト 2 人、`--namesake N`）

「佐藤健」が 2 人いる。会社も携帯もメールも違う。**誤検知されないか**を確認する。

期待：`full_name` のみ一致 → `possible_low` の DC が pending で生成される。レビュー画面で「別人」判定すると以後同じペアは検出されない（§8.9 different_person 永続性）。
DC 期待件数：N=2 で 1 件（2C2 = 1）。

#### グループ⑤ ノイズ（デフォルト 10 人、`--noise N`）

絞り込みアルゴリズム（§8.10）が正しく除外することを確認するため、全く似ていない人を混ぜる。
DC 期待件数：0 件。

### 2.7 オプション一覧

```
python manage.py dev_create_test_contact_data \
  [--clone N]              # グループ① 件数（デフォルト 5）
  [--career N]             # グループ② 件数(デフォルト 4)
  [--namechange N]         # グループ③ 件数(デフォルト 3)

  [--dry-run]              # DB に書かず内容表示
  [--verbose]              # 詳細表示
```

### 2.8 ContactFieldConfidence の3モード（`--confidence-mode`）

§10.6.4 の整理に従う。OCR 由来 Contact を再現するため、3 モードで挙動を切り替える。

#### random モード（デフォルト）

OCR 結果の現実的な分布を再現：

- `full_name`：80% high / 20% medium
- `email`：70% high / 25% medium / 5% low
- `mobile` / `phone` / `fax`：70% high / 25% medium / 5% low
- `company`：75% high / 20% medium / 5% low
- `department` / `title` / `branch`：65% high / 25% medium / 10% low
- `address`：60% high / 30% medium / 10% low

high のフィールドは ContactFieldConfidence レコードを作らない（§4.6.1 の CheckConstraint により high は DB に保存できない）。low / medium のみレコードを作成し、`confirmed_at` は NULL（未確認状態）。

#### high モード（全 high 扱い）

ユーザーが全フィールド確認した状態を再現するモード。実装方法は次のいずれか：

- 案A：ContactFieldConfidence レコードを作らない（デフォルトで全 high 扱い、§10.6.4 ケース1 相当）
- 案B：low / medium レコードを作りつつ `confirmed_at` を埋める（§10.6.4 ケース2 相当の「確認済み」状態）

実装方針はコード君A に委ねる。検証用途の違い（新規作成 Contact の再現か、修正済み Contact の再現か）で使い分ける場面があるため、両案を併記しておく。コード君A が選択しやすい一方で実装する形で問題ない。

#### custom モード

`--high-fields full_name,email` のように指定したフィールドだけ high、残りは random と同じ分布。

### 2.9 ContactFieldConfidence の生成上の制約（必読）

§4.6.1 の DB 制約により：

- `confidence='high'` の ContactFieldConfidence レコードは作れない（CheckConstraint で物理的に禁止）
- `confidence` は `'low'` または `'medium'` のみ
- 「high 扱い」を表現するときは、レコードを作らない（または low/medium レコードに `confirmed_at` を埋める）

直接 `ContactFieldConfidence(confidence='high').save()` を呼ばないこと。

## 3. やってはいけないこと

### 3.1 BusinessCard / OriginalImage を作らない

OCR 経路を再現するスクリプトではない。Contact + Person + ContactFieldConfidence のみ生成する。`Contact.business_card = None` で作成する（X-2 補足で `null=True, blank=True` 対応済み）。

### 3.2 DuplicateCandidate を直接作らない

DC は cron（`Run_Generate_Duplicate_Candidates`）が生成するもの。スクリプトは「テストデータの土台」を作るのみ。DC の生成テストは別途 `python manage.py check_duplicates --limit 100` で行う。

### 3.3 confidence='high' レコードを作らない

§4.6.1 の DB 制約に違反する。`ContactFieldConfidence` のレコードは `confidence='low'` または `confidence='medium'` のみ。

### 3.4 test_data_user を勝手に作らない

Django Admin で事前作成する前提。存在しなければエラー終了させる。

### 3.5 cron を内部で起動しない

スクリプトはテストデータ生成のみ。cron 起動・DC 検証・通しチェックは別途手動で実施する。

### 3.6 正規化関数を再実装しない

Contact のフィールド値はプール時点で正規化済みの形（数字のみの電話番号、小文字のメール、空白除去済みの会社名）で持つ。`contacts/services/normalization.py` の関数を呼ぶ必要はない（呼んでも問題ないが、プール側で正規化済みの値を持てば二度手間）。

### 3.7 コミット&プッシュを自己判断で行わない

実装完了後、サポート担当クロード君（このチャット）の確認 → たんたん OK → 指示を受けてからコミット&プッシュする。

## 4. 動作確認方法

### 4.1 デフォルト実行

```
python manage.py dev_create_test_contact_data
```

期待出力：

- 生成 Person 数：24
- 生成 Contact 数：24（`status='primary'`、`business_card=None`）
- 生成 ContactFieldConfidence 数：random モード分布に従う件数（おおよそ 30〜80 件）
- グループ別件数の表示（①5 / ②4 / ③3 / ④2 / ⑤10）

### 4.2 --dry-run で内容確認

```
python manage.py dev_create_test_contact_data --dry-run --verbose
```

期待出力：DB に書き込まずに、生成予定の Person / Contact / ContactFieldConfidence の内訳を表示。

### 4.3 --reset で既存テストデータを消してから再生成

```
python manage.py dev_create_test_contact_data --reset
```

期待出力：`test_data_user` が `created_by` の Contact / Person / ContactFieldConfidence / DuplicateCandidate / PersonMergeLog / ActionLog をすべて削除し、その後新規生成する。

### 4.4 cron 連携の通しチェック（参考、本タスク範囲外）

テストデータ生成後、`python manage.py check_duplicates --limit 100` を実行し、DuplicateCandidate が期待通り 20 件生成されることを確認する。これはスクリプト実装の範囲外だが、最終的な動作確認時にたんたんが手動で行う。
