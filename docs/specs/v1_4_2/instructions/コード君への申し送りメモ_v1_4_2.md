## 3. 実装上の最重要注意

### 3.1 重複チェックの 2 段階ロック方式（v0.1.5 の 4.4）

`Run_Generate_Duplicate_Candidates` の実装で、統合最終版 12.4 の「1 Contact ごとに transaction.atomic() で囲む」だけを読んで素朴に実装すると、以下の問題が発生する：

- **問題 1**：全体を `transaction.atomic()` で囲むと、ループ中の 1 件失敗で全件ロールバックされる（rev5 12.6 のエラーハンドリング方針と矛盾）
- **問題 2**：`select_for_update` を `transaction.atomic()` 外で呼ぶと `TransactionManagementError` が発生する
- **問題 3**：ロック取得直後に状態チェックをしないと、状態変化が起きた Contact を処理してしまい partial unique constraint 違反（`IntegrityError`）が発生する

正しい実装パターンは v0.1.5 の 4.4 に詳述されている：

1. **ステップ A**：対象 Contact の **ID リスト**を取得する。`transaction.atomic()` の外で実行する。ロックは取らない
2. **ステップ B**：ID リストを 1 件ずつループし、各 contact_id について：
   - `with transaction.atomic():` を開始
   - `Contact.objects.select_for_update(skip_locked=True).filter(id=contact_id).first()` でロック取得
   - **3 段再チェック**を実施（`duplicate_checked_at` / `Contact.status` / `Person.status`）
   - すべて OK なら `generate_duplicate_candidates_for_contact(contact)` を呼ぶ

実装の詳細は v0.1.5 の 4.4 と 4.4.1 / 4.4.2 / 4.4.3 を必ず参照すること。

### 3.2 Form は DB に触らない

`form.get_update_contact()` は **新規 Contact インスタンス（pk なし）を返すだけ**。DB 書き込みは View またはサービス層が判断する。

- 修正画面（12 / 13 番）：View 内で `change_reason` に応じて既存 Contact 上書き or 新規 Contact 作成を判断
- マージ画面（17 番）：サービス層（`Execute_Merge_with_Updates`）に渡し、サービス層内で適切に処理

詳細は統合最終版 11.6 / 11.7 を参照。

### 3.3 PDF 表に逆らわない

マージ画面の status 遷移実装中、「サバイブ側 Contact の previous_* も記録すべきでは？」と思っても、**サバイブ側 Contact の `previous_*` は変更しない**（PDF 表ポリシー、統合最終版 9.4.1）。Django の `update_fields=['status']` で限定 save する実装パターンを使う。

### 3.4 same_card 修正ありの特殊扱い

`Execute_Merge_with_Updates` の `merge_reason='same_card'` のときだけ、他の merge_reason と挙動が違う：

- サバイブ側既存 primary を**直接更新**（status は primary のまま、フィールド値だけ部分更新）
- 新規 Contact は**作らない**
- ContactFieldConfidence は `mark_fields_as_confirmed` で**部分 confirmed 化**

`contact.fix(form, user)` は **呼ばない**（fix は全 confirmed 化なので責務が違う）。詳細は統合最終版 9.4.5 を参照。

### 3.5 切り分け基準は「フィールド修正の有無」（統合最終版 9.4.4）

`Execute_Merge_Only` か `Execute_Merge_with_Updates` かの切り分けは **「フィールド修正の有無」** であり、**merge_reason ではない**。`merge_reason` は両サービスとも 7 値すべて受け付ける。誤って merge_reason で分岐させないこと。

### 4.2 Contact.update_target_fields() の定義

統合最終版 5.1（`contact.fix` の実装イメージ）で `Contact.update_target_fields()` を呼んでいるが、本文中に明示的な定義がない。実装方針：

- **クラスメソッドとして実装**
- 戻り値は **`ContactBaseForm.Meta.fields` を参照**（二重管理を避ける）

例：

```python
@classmethod
def update_target_fields(cls):
    from contacts.forms import ContactBaseForm
    return list(ContactBaseForm.Meta.fields)
```
