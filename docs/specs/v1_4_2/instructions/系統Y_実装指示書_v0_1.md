## 2. 実装範囲

### 2.1 invalidate_pending_candidates(contact)

仕様書 §12.7.2 の処理内容通り：

1. contact が紐づく Person を特定
2. その Person を person_a または person_b に持つ DuplicateCandidate のうち review_status='pending' のものを invalidated に変更
3. contact.duplicate_checked_at = NULL に戻す

### 2.2 recover_duplicate_candidates(merged_person, surviving_person)

仕様書 §12.8.3 の手順1〜3 を実装。**手順4 は実装しない**（後述 §3.1 参照）。

1. merged_person を含む他の pending DC を invalidated 化（A / B 以外の Person 集合を保持）
2. 当該マージの DC を 'merged' に変更
3. 保持した DC を再復帰：
   - `DuplicateCandidate.create_recovered_from(old_candidate, surviving_person)` クラスメソッド経由で新規作成
   - score / rank / matched_fields / group_id は old_candidate からコピー（再計算しない）
   - merged_person だった側を surviving_person に置き換え
   - review_status='pending' で作成
   - **再復帰の除外条件**：相手側 Person が active 以外（merged / archived）なら復帰させない（§12.8.3 末尾）

## 3. 確定論点（過去議論済み、再走禁止）

以下はサポート担当クロード君（別チャット）との過去議論で決着済みの内容。**仕様書側の修正は別途オーパス君（仕様書改訂担当）が行う予定**だが、現時点では古い記述が一部残っている。新しいクロード君や AI レビュアーが「仕様書ではこう書いてある」と再走させやすいポイントなので、必ず明示する。

### 3.1 §12.8.3 手順4「duplicate_checked_at の更新」は recover に含めない

仕様書 §12.8.3 手順4 で「surviving_person.duplicate_checked_at の更新（has_field_updates 分岐）」が recover の処理として書かれているが、**これは古い記述**。

確定方針:duplicate_checked_at の更新は呼び出し元(Execute_Merge_Only / Execute_Merge_with_Updates)の責務。recover 関数内には実装しない。

理由:「recover は DC 復帰のみ」「duplicate_checked_at は呼び出し元」という責務分離。recover を内部ヘルパーとして純粋に保つ。

### 3.2 has_field_updates 引数を追加しない

recover のシグネチャは仕様書 §13.4.3 通り：

```
recover_duplicate_candidates(merged_person, surviving_person)
```

has_field_updates 引数は追加しない。値修正の有無を問わず同じ処理を適用する（recover 一本化、§12.8.1）。

duplicate_checked_at の更新方針は呼び出し元が分岐：

- Execute_Merge_Only → `surviving_person.primary_contact.duplicate_checked_at = timezone.now()`
- Execute_Merge_with_Updates → `surviving_person.primary_contact.duplicate_checked_at = None`（次回 cron で再判定）

### 3.3 ActionLog を書き込まない

両関数とも ActionLog 書き込みは含めない。書き込みは呼び出し元（contact.fix、Execute_Merge_Only / Execute_Merge_with_Updates）の責務。

理由:1ユーザー操作 = 1 ActionLog の原則。invalidate / recover は内部処理ヘルパーとして純粋に保つ。

### 3.4 関数内に `transaction.atomic()` を切らない

両関数とも関数内で `transaction.atomic()` を切らない。呼び出し元(contact.fix、Execute_Merge_*)が atomic で囲む前提。

仕様書 §12.7.2 末尾「これらを呼び出し元のトランザクション内で実行する」、§9.3.1 手順9 で明示済み。

### 3.5 invalidate_pending_candidates を recover の中で呼ばない

§12.8.3 手順1「merged_person を含む他の pending DC を invalidated 化」は `invalidate_pending_candidates` の処理内容と似ているが、**recover は invalidate を呼ばず、独自クエリで処理する**。

理由:`invalidate_pending_candidates` は §12.7 専用ヘルパー(contact 引数、duplicate_checked_at=NULL も同時に更新)。recover の手順1 とは引数も処理範囲も異なる。責務分離のため共通ヘルパー化しない。

### 3.6 スコアを再計算しない

**§12.8.4 を必読**。「スコアコピーはおかしい、再計算が必要」という指摘は過去複数のレビュー（GPT・Opus 含む）で却下されている。Opus レベルでも 2 回連続で同じ誤解を起こした実績あり。

`DuplicateCandidate.create_recovered_from()` クラスメソッド経由でスコア・ランク・matched_fields・group_id をコピーで実装する。

「コンタクトの値がマージで変わっても、対象人物が同一人物である可能性は変わらない。スコア・ランクは『2 つの Person が同一人物である可能性の指標』であり、人物そのものに紐づく値」が中心ロジック。

## 4. やってはいけないこと

1. **duplicate_checked_at の更新を recover に含めない**:呼び出し元責務
2. **has_field_updates 引数を追加しない**:シグネチャは仕様書 §13.4.3 通り
3. **ActionLog を書き込まない**:呼び出し元責務
4. **関数内 `transaction.atomic()` を切らない**:呼び出し元 atomic 前提
5. **invalidate_pending_candidates を recover の中で呼ばない**:独自クエリで実装
6. **スコアを再計算しない**:`create_recovered_from()` でコピー
7. **`DuplicateCandidate.objects.create()` を直接呼ばない**:必ず `create_recovered_from` クラスメソッド経由(モデル側に集約済み)
8. **コミット&プッシュを自己判断で行わない**

## 5. 動作確認方法

C ブロック（マージ実行サービス）がまだ実装されていないため、本タスクでは呼び出し元経由の通しチェックは行えない。Django shell で関数を直接呼ぶ単体的な確認まで。

### 5.1 テストデータ準備

```
python manage.py dev_create_test_contact_data --reset
```

24 人のテストデータを生成。続いて：

```
python manage.py check_duplicates --limit 100
```

DC が 20 件生成されることを確認。

### 5.2 invalidate_pending_candidates の単体動作確認

`python manage.py shell` で：

- グループ① の山田太郎（5人いる Contact のうち 1 つ）を取得
- `invalidate_pending_candidates(contact)` を `transaction.atomic()` 内で呼ぶ
- 当該 Person を person_a / person_b に持つ pending DC が invalidated になっていること
- contact.duplicate_checked_at が NULL に戻っていること

### 5.3 recover_duplicate_candidates の単体動作確認

`python manage.py shell` で：

- グループ② career_A と career_B の Person を取得（同一フルネーム・同一会社で関連性が強いペア）
- 仮想的にマージ後の状態を作る（surviving_person / merged_person）
- `transaction.atomic()` 内で `recover_duplicate_candidates(merged_person, surviving_person)` を呼ぶ
- merged_person 縁故の他 pending DC が surviving_person 起点に置き換わって pending で再作成されていること
- スコア・ランク・group_id がコピーされていること
- 当該マージの DC が 'merged' に変更されていること
- 相手側 Person が active 以外なら復帰されないこと（手動で 1 件 archived 化して確認）

通しチェック(cron 連携・C ブロックからの呼び出し)は C ブロック実装後に行う。
