## #1 has_minimum_info NG 時の BusinessCard 残置（方針確定・要確認事項解消）

**対象仕様書**：統合最終版

### 項目名
has_minimum_info で弾かれたケースでも BusinessCard を生成する仕様への変更（方針確定）

### 現状仕様（仕様書の該当章節）

**第15章 §15.1 cards 処理ルール一覧**（行 2497-2507）

| ID | ケース | 処理 |
|---|---|---|
| C3 | 全 card が has_minimum_info で弾かれた | status=extracted（BusinessCard 0 件）、error_message に記録 |

### 改訂内容（確定版）

C3 の処理を以下に変更する。

- has_minimum_info で弾かれた card に対しても **BusinessCard は生成する**
- ただし **Contact / Person は作らない**
- BC の `ocr_result` フィールドに `'insufficient_info'` をセット（#9 参照）
- error_message には記録しない（silent skip、コードが現実、案A方針）

詳細な §15.1 改訂内容は #10 を参照。BusinessCard モデル変更は #9 を参照。

### 改訂理由

1. **ユーザー使い勝手**：撮り直し判断の材料として「OCR が何を読み取ったのか」を確認できる
2. **OpenCV データ収集**：検出精度改善のため、has_minimum_info NG ケースの実データを蓄積する
3. **デバッグ性**：処理した事実を BusinessCard として残すことで、後追い検証が可能になる

### 影響範囲

- §15.1 ルール C3 の処理内容修正（→#10）
- §4.3 BusinessCard モデルへの ocr_result フィールド追加（→#9）
- §4.3 BusinessCard と §4.4 Contact の関係性の整理（→#11）
- §14.4 モデル固有の TextChoices に BusinessCard.OcrResult を追加（→#9）
- 別表 C に BusinessCard.OcrResult セクション追加（→#9）
- 別表 A.4 BusinessCard フィールド対照表に ocr_result 追加（→#9）
- マイグレーション必要（BusinessCard テーブルに ocr_result カラム追加）

### 確定経緯

- 2026-05-07 たんたんから方針確定の連絡（B 側サポートチャットでの提案を受けて）
- 2026-05-07 たんたんと B 側サポートクロード君で方針詳細を詰め、要確認事項3点解消
- 2026-05-07 B 側サポートクロード君から仕様書改訂担当オーパス君へ報告書受領

### 担当ブランチ

**B 側（feature/opencv-improvement）** ※初版で「A側または要確認」としていたが、B 側に確定

理由：A 側は Contact / Person / Duplicate / ActionLog 関連の作業、B 側は OCR パイプライン側の作業。BC 残置仕様変更は OCR パイプライン側の話なので B 側で実装する。

### マージタイミング

要確認のまま。ocr_result フィールド追加だけなら A 側に影響なし見込み（A 側は BC モデルを触っていない前提）が、念のため A 側マージ時に確認する。

### ステータス

ステップ1（モデル変更）実装済み。ステップ2（UI改善）も実装済み（コミット 3ceacb6）。仕様書側の記述追加のみ残っている。

### 要確認事項の解消結果

| 当初の要確認事項 | 解消結果 |
|---|---|
| Contact のない BusinessCard の判別方法 | BC 側に ocr_result フィールドを新設して区別。当初の暫定案「Contact 側からの逆引き、モデル変更なし」は不採用。理由：(1)将来拡張に強い、(2)集計クエリが書きやすい、(3)ビュー・テンプレート側の判別ロジックが分散しない、(4) v1.4.x のデータ収集（OpenCV 改善のため）に有用 |
| ユーザーへの通知文言・通知方法 | 今回のスコープでは決めない。ステップ2の UI 実装でコード君に任せる方針（たんたん判断）→ ステップ2 で #14（ocr_result_badge）として実装済み |
| ケースA／ケースB の区別方法 | is_business_card 判定で機械的に区別。ケースA → is_business_card=False → ocr_result='not_business_card'、ケースB → is_business_card=True かつ has_minimum_info NG → ocr_result='insufficient_info'、ケースB派生（card 単位の OCR 例外）→ ocr_result='ocr_failed'（将来用、ステップ2以降） |

**(7) post_delete シグナルによる FS 実体自動削除の言及**

§4 末尾、または §11 アプリケーション設計の補足節として、以下の設計思想を簡潔に明記する（具体的位置はオーパス君判断）：

### 改訂理由

## #19 X-3 ランナバグ修正に伴う v0.1.5 詳細仕様書の改訂

**対象仕様書**：v0.1.5 詳細

### 項目名
Run_Generate_Duplicate_Candidates_詳細仕様書 v0.1.5 の §3.6 / §3.6.1 / §3.4（処理フロー）/ §5.3 / §5.4.1 を、X-3 ランナバグ修正で確定した「事前フィルタロジック」を反映する形に改訂する

### 現状仕様（仕様書の該当章節）

**v0.1.5 §3.6 partial unique constraint との関係**

> ただし、本仕様の運用では以下の理由により、この衝突は実運用上発生しない想定とする。
> - 12.7 の処理が Contact 編集時に必ず発火し、関連 pending を invalidated 化する
> - マージ実行時の recover 処理（rev5 7.3）が同 Person ペアの pending を整理する
> - duplicate_checked_at = NULL の Contact のみが本関数の処理対象となるため、過去 pending の存在は cron 起動時点では想定されない
> - 上位関数 Run_Generate_Duplicate_Candidates の 4.4.3 で 3 段の再チェックを行うため、ロック取得から processing までの間の状態変化による競合経路は排除される

→ この前提は「12.7 / recover が事前に整理する経路でのみ pending DC が作られる」想定だが、新規 OCR 取り込みで同一名刺ペアの両側が同一 cron バッチに入るケースや、テストデータ生成スクリプト経由の流入では成立しない。実装で X-3 修正により事前フィルタを追加したため、仕様書側もこれに合わせる必要がある。

**v0.1.5 §3.3 generate_duplicate_candidates_for_contact の処理フロー**

現状の手順 (3) と (4) の間に、事前フィルタの記述がない。

**v0.1.5 §5.4.1 なぜ履歴参照判断を generate 側に集約するか**

現状の責務分担記述では「履歴参照判断は different_person 除外と group_id 発行のみ」と読める。X-3 修正で「既存 pending DC の存在チェック」も generate 側の履歴参照判断として加わったため、責務一覧に明記が必要。

### 改訂内容

**(1) §3.6 の書き換え**

「実運用では発生しない想定」の記述を削除し、「事前フィルタで衝突自体を回避する」方針に書き換える。具体的には：

- 12.7 / recover が事前に整理する経路で「衝突を未然に防ぐ」想定だった部分を削除
- 代わりに「同一 cron バッチ内で同 Person ペアの両側が処理対象になるケース（新規 OCR 取り込み・テストデータ流入等）でも、事前フィルタで衝突を回避する」と明記
- 4.4.3 の 3 段再チェックは引き続き有効、これは事前フィルタとは別レイヤーの防御である旨を明記

**(2) §3.6.1 の書き換え**

現状「IntegrityError 発生時の挙動（v0.1.2 で確定）」として記述されているが、事前フィルタ追加により IntegrityError は発生しない想定に変わる。記述を以下の方向で書き換え：

- ignore_conflicts=True を付けない方針は維持（v0.1.2 確定）
- 万一 IntegrityError が発生した場合は、事前フィルタの実装漏れまたは race condition の証拠であり、当該 contact のトランザクションをロールバックして上位ループに伝播させる（既存の §1.3 / §4.5 と整合）

**(3) §3.3 処理フローへの事前フィルタステップ追加**

現状の手順を以下の構成に変更：

- 現状の手順 (3) と (4) の間に、新たに **手順 (3.5) 事前フィルタ** を挿入
- 手順 (3.5) の内容：「contact.person と既に pending DC として組まれている Person ID 集合を、person_a / person_b 別々の 2 クエリで取得し、その集合に含まれる候補をスキップする」
- SQLite 3.51.2 planner bug 回避のため Q(person_a=p) | Q(person_b=p) は使わない旨を補足
- スキップ判定は person_id レベルで行う旨を明記
- 手順番号は (3.5) として挿入するか、全手順番号を振り直すかはオーパス君判断

**(4) §3.4 DuplicateCandidate インスタンスの各フィールドの値**

特に変更なし。事前フィルタで除外された候補は DuplicateCandidate インスタンスを構築する手順自体に到達しないため、フィールド値定義は影響を受けない。

**(5) §5.3.2 cron 新規生成時の group_id 発行ロジック**

「事前フィルタで生き残った候補のみに group_id 発行を適用する」旨を補足。フィルタで除外された候補には group_id 発行を行わない（DuplicateCandidate インスタンス自体を作らないため自然にそうなる）が、明文化しておくと読みやすい。

**(6) §5.4.1 履歴参照判断の責務一覧に追記**

現状「履歴参照判断（different_person 除外、group_id 発行）はすべて generate_duplicate_candidates_for_contact 側で実施し」と書かれている部分を、以下に拡張：

- 履歴参照判断（different_person 除外、group_id 発行、**既存 pending DC の存在チェック**）はすべて generate_duplicate_candidates_for_contact 側で実施する
- 「DB 履歴を見る判断」の責務が generate 側に一極集中する設計趣旨は維持

**(7) §6.2 確認観点への追加**

確認観点 #8 として「同 cron バッチ内で同 Person ペアの両側が処理対象になっても IntegrityError なしで完走する」観点を追加。テストデータ生成スクリプト dev_create_test_contact_data --reset → check_duplicates --limit 100 で再現可能な手順として記載。

### 改訂理由

X-3 ランナバグ修正（コミット 4cd1c3e）で、partial unique constraint 違反を事前フィルタで回避する実装が確定した。仕様書側の前提記述（「実運用では発生しない想定」）と実装が乖離している状態を解消する。

### 影響範囲
