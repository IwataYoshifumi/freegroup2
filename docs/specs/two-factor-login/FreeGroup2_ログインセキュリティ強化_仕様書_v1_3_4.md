## 1. 目的と範囲

**目的**：不正ログインを「防ぐ」「遅らせる」「気づく」の3点で強化する。

| 機能 | 役割 | 章 |
| --- | --- | --- |
| ログイン失敗ロック | 総当たりを遅らせる | §5 |
| 二段階認証（認証アプリ＋リカバリーコード） | パスワード漏洩だけでは入れないようにする | §6 |
| ログイン通知メール | 本人と管理者が不正アクセスに気づく | §7 |

3機能は同じログインフローに割り込むため、処理順（§4）を1本の仕様書で定義する。

**範囲外（本仕様書では作らない）**：メール／SMS でのワンタイムコード、パスキー（WebAuthn）、SSO（SAML／OIDC）、重要操作前の再認証、パスワードポリシー、パスワード変更・パスワードリセット機能そのもの（**別仕様書「パスワード変更・リセット 仕様書」で定める**。本仕様書には §14-9 に制約のみ記載）。

## 2. 確定した設計判断

| # | 論点 | 決定 | 理由 |
| --- | --- | --- | --- |
| 1 | 仕様書の範囲 | 3機能を1本にまとめる | 処理順の定義を文書間で割らないため |
| 2 | 第二要素の方式 | 認証アプリ（TOTP）＋リカバリーコード | メール方式はメール乗っ取りで突破される |
| 3 | LDAP ユーザー | 認証元に関係なく FG2 側で第二要素を要求 | LDAP バインドでは AD 側の多要素認証が効かない |
| 4 | 強制レベル | 任意／管理者のみ必須／全員必須。**画面から設定** | 方針は導入先の管理者が決める。SaaS 化でテナント別に持てる |
| 5 | 端末紛失時 | 管理者がリセット。最終手段は管理コマンド | — |
| 6 | リカバリーコードも紛失 | 同上。**メールでの自己リセットは設けない** | メール乗っ取りで第二要素ごと突破されるため |
| 7 | 管理者の人数 | **2名以上を推奨**（強制せず、1名のとき警告表示） | 管理者自身の締め出しを防ぐ |
| 8 | 信頼済み端末 | あり（既定30日、第二要素を省略） | 毎回入力だと任意設定の導入先で使われない |
| 9 | ログイン通知レベル | 毎回／新しい端末のみ。**画面から設定**、初期値は毎回 | いつもの端末からの不正にも気づくため |
| 10 | 通知なしの選択肢 | 設けない。新しい端末は常に通知 | 「気づく」目的が消えるため |
| 11 | ロック発生の通知 | 通知レベルの対象外。常に送る | 異常事態のため |
| 12 | 通知の個人設定 | 不可（導入先全体で1設定） | 乗っ取った側が通知を絞れてしまう |
| 13 | 実装基盤 | django-otp（秘密鍵の保管とコード検証のみ利用）。画面は自作。**django-otp のミドルウェアと「第二要素を通ったか」の判定機能は使わない**（§14-17）。**対応バージョンのみを前提とし、非対応時の代替実装は用意しない** | 付属画面を持つライブラリは HIG と衝突する。Django 6.0.2 での動作は検証済み（§3） |
| 14 | ユーザー個別の必須・免除 | **設けない**。必須かどうかは強制レベルだけで決まる | 免除されたアカウントが最も狙われる穴になる |
| 15 | 管理者宛通知の絞り込み | ロック発生・IP 遮断の管理者宛通知は設定画面で送る／送らないを選べる。リセットと「弱める変更」の通知は常に送る | 運用しながら絞れるようにする。後者2つを切れると、乗っ取った管理者が通知を止めてから設定を緩められる |
| 16 | セッション切断 | 管理者リセット・本人の再登録・無効化の時に、対象ユーザーの他のセッションを切る | 盗まれたセッションを残さない |
| 17 | 実装ブランチ | main から分岐。AccessList は本機能の後に再実装 | マイグレーション番号とファイルの競合を避ける |
| 18 | 接続元 IP の取得 | **入口を nginx に一本化**し、Cloudflare 経由の補正は nginx で行う。Django は nginx が付ける値だけを読む（§5.7） | 本番は Cloudflare 経由と LAN 直を併用している。Django 側で複数のヘッダを読み分けると LAN から偽装できる |
| 19 | LDAP 同期 | **本機能では変更しない** | ライブラリ本体も毎回ユーザーを保存するため、同期側だけ直しても保存はなくならない。旧 AccessList は変更を検知してから再計算する作りで実害は小さい |
| 20 | リカバリーコードの保存 | サーバーの秘密鍵を使った**鍵付きハッシュ**で保存する（パスワード用のハッシュ方式は使わない） | パスワード用ハッシュは10個の照合に約2.2秒かかり（実測）、連打で3ワーカーが塞がる。鍵付きハッシュは DB だけが漏れても突破できず、照合も一瞬で済む |
| 21 | 「管理者全員」の範囲 | 有効な**管理者ロール保持者とスーパーユーザー** | 管理者ロールは Django 管理画面でしか付与できず、スーパーユーザーしかいない導入先では宛先が0名になる |
| 22 | メールの送信方法（v1.3.2） | **共通のメール送信部品を本機能で新設**し、通知メールはすべてこれで送る（§7.6）。メール配信機能の送信処理は流用しない | 汎用の送信関数が FG2 にない。見積書DB（v1.9）でも同じ部品を使うため、最初に必要になる本機能で作る |

## 4. ログインフロー全体（処理順）

この順序を変えてはならない。番号は §14 の厳守事項と対応する。

| 順 | 処理 | 失敗・分岐時 |
| --- | --- | --- |
| 1 | 接続元 IP を取得し、**IP 遮断中か判定** | 遮断中 → 共通エラー表示。認証処理に進まない |
| 2 | 入力ユーザー名に該当するユーザー（特定の規則は §5.1）の**アカウントロック中か判定** | ロック中 → 共通エラー表示。**認証処理（LDAP バインド含む）を呼ばない** |
| 3 | 第一要素の認証（既存の認証バックエンドをそのまま使用。ローカル／LDAP） | 失敗 → 失敗を記録（§5）。共通エラー表示 |
| 4 | 第二要素が必要か判定（§6.4）。**端末識別クッキーと端末記録の照合はここで行う**（結果を順8まで保持） | 不要 → 順7へ |
| 5 | **仮認証状態**にして第二要素入力画面へ（ログイン済みにはしない）。仮認証の内容は**セッションに保存**する（ログイン前の匿名セッション） | 仮認証は5分で失効 → ログイン画面へ戻す |
| 6 | **IP 遮断とアカウントロックを再判定**したうえで、認証アプリのコードまたはリカバリーコードを検証 | 遮断・ロック中 → 仮認証を破棄し共通エラー表示。検証失敗 → 失敗を記録（§5）。同じ失敗回数に加算 |
| 7 | **セッション確立**（ここで初めてログイン済み）。連続失敗回数を0に戻す | — |
| 8 | 端末記録の更新（順4の照合結果で「新しい端末か」を確定してから、最終ログイン日時の更新・信頼登録を行う） | — |
| 9 | ログイン試行記録に「成功」を記録 | — |
| 10 | ログイン通知メールを送信（§7） | 送信失敗でもログインは成立させる |
| 11 | 二段階認証が必須なのに未登録なら登録画面へ強制誘導（§6.5）。それ以外は元の遷移先へ | — |

**共通エラー表示**：順1〜3の失敗と、順6での遮断・ロックは、すべて同じ文言「ログインできません。入力内容を確認するか、しばらく待ってから再度お試しください。」とする。ユーザーの存在有無やロック状態を画面から推測させないため。ロックの事実は本人宛メール（§5.5）で伝える。

- **順6で再判定する理由**：仮認証の5分間に、別のブラウザからの失敗で同じアカウントがロックに入ったり、IP 遮断に達したりすることがある。再判定しないと、ロック中でもコードの検証を続けられてしまう。
- **応答時間の差は許容する**：ロック中は認証処理を呼ばないため、通常の失敗より速く応答する。この差からロック状態を推測される可能性はあるが、ロック中に LDAP へ流さない利点（§5.3）を優先する。
- **遷移先の安全確認**：ログイン後の遷移先（既存ログイン画面の hidden 項目で渡される値）は、自サイト内の URL であることを確認してから使う。確認に通らない値は捨てて既定の遷移先（ホーム）へ送る。仮認証をまたぐ場合も同じ。

## 5. ログイン失敗ロック

### 5.1 アカウントロック

| 項目 | 仕様 | 初期値（設定可能範囲） |
| --- | --- | --- |
| ロック条件 | 同一ユーザーへの連続失敗が「セキュリティ設定．ロック失敗回数」に達する | 5回（3〜10） |
| ロック時間 | 「セキュリティ設定．ロック時間（分）」が経過すると**自動解除** | 15分（5〜1440） |
| 失敗に数えるもの | パスワード失敗、**第二要素のコード失敗**（認証アプリ・リカバリーコードとも） | — |
| 連続の定義 | 前回の失敗からロック時間以上あいた場合は1回目から数え直す | — |
| 回数を0に戻す時 | **ログインが最後まで成立した時のみ**（§4 順7）。第一要素の成功だけでは戻さない | — |
| ロック中の試行 | 正しいパスワードでも拒否。回数にもロック時間の延長にも数えない | — |
| 手動解除 | 権限「二段階認証リセット」を持つ管理者が、ユーザー詳細画面から解除できる | — |

- ロック中の試行を延長に数えないのは、攻撃者が試行を続けるだけで正規ユーザーを永久に締め出せてしまうため。
- 存在しないユーザー名への試行はアカウントロックの対象がないため、IP 遮断（§5.2）だけで数える。

**ユーザーの特定規則**（ロックの判定と失敗の加算で共通）

- 入力ユーザー名は、前後の空白を除き、**大文字小文字を区別せずに**ユーザーを特定する。
- 完全に一致するユーザーがいれば、それを優先する。
- 大文字小文字だけが違うユーザーが複数いて完全一致がない場合は、該当する全員を対象とする（1人でもロック中なら拒否。失敗は全員に加算）。
- ログイン試行記録の「ユーザー」欄は1人分しか持てない。記録するのは、完全一致のユーザー、なければ該当者のうち ID が最小の1人とする。
- 理由：LDAP 認証は大文字小文字を区別せずにユーザーを探す。区別して特定すると、ロック中の「taro」に対して「TARO」と入力するだけでロック判定を素通りし、LDAP への認証試行が続けられる。失敗も別名義で数えられ、ロックに達しない。

### 5.2 IP 遮断

- 同一 IP からの失敗（パスワード失敗・コード失敗）が直近15分で「セキュリティ設定．IP遮断失敗回数」（初期値20、設定可能範囲10〜100）に達したら、その IP からのログイン試行を拒否する。
- 判定はログイン試行記録の件数から都度計算する（専用の状態は持たない）。直近15分の件数が閾値を下回れば自動的に解除される。
- ユーザー名を変えながら試す攻撃（パスワードスプレー）への対策。社内 NAT で複数人が同じ IP になるため、閾値はアカウントロックより大きくする。
- **IP 遮断中は、同じ IP から来る正規ユーザーもログインできない**（ログイン済みのセッションには影響しない）。社内の複数人の入力ミスが重なって閾値に達することもあるため、遮断が頻発する導入先は閾値を上げる。

### 5.3 LDAP 利用時の注意

- FG2 がロック中の試行を LDAP に流さない（§4 順2）ことで、FG2 経由の総当たりで AD 側アカウントがロックされるのを防ぐ。
- 運用上、FG2 のロック失敗回数は AD 側のロック閾値**以下**に設定することを設定画面に注記する。
- **一度もログインしていない LDAP ユーザーにはアカウントロックが効かない**。FG2 のユーザーは LDAP での初回ログイン成功時に作られるため、それ以前は「存在しないユーザー名」として扱われ、防御は IP 遮断だけになる。設定画面にもこの旨を注記する。

### 5.4 状態の保存場所

- 連続失敗回数とロック期限は「アカウントロック」モデルに保存する（ユーザーと1対1）。キャッシュは使わない。
- 並行して届いた試行で回数を取りこぼさないよう、**加算は DB 側の加算式で行う**（読み出してから +1 して保存する方式・行ロックに頼る方式は使わない）。開発環境の SQLite では行ロックが効かず、本番の PostgreSQL と挙動が変わるため。
- 「ロックに入った瞬間」は、ロック期限の書き込みを条件付きの更新（まだロックされていない行だけを更新）で行い、**更新できた件数が1件の時**と判定する。並行した試行があっても、ロック発生の通知と操作ログは1回だけになる。
- **加算と数え直しは1回の更新で行う**。「前回の失敗からロック時間以上あいていれば1に戻し、そうでなければ +1 する」を、条件分岐つきの1つの更新にまとめる。数え直しと加算を別々の更新にすると、並行した試行で取りこぼしが出る。
- アカウントロックの行は最初の失敗時に作る。同時に届いた失敗で作成が競合した場合は、重複エラーを受けて作成済みの行を使い直す（再試行で吸収する）。

### 5.5 ロック時の通知

| 事象 | 宛先 | タイミング |
| --- | --- | --- |
| アカウントロック発生 | 本人（常に送る）＋ 管理者全員（設定で送らないにできる） | ロックに入った瞬間に1回（ロック中の拒否では送らない） |
| IP 遮断発生 | 管理者全員（設定で送らないにできる） | 失敗を記録した結果、直近15分の件数が閾値に達し、**かつ同じ IP の遮断発生を直近15分に操作ログへ記録していない時**に1回 |

「管理者全員」＝有効な管理者ロール保持者とスーパーユーザーのうちメールアドレスがある者（本仕様書で共通）。管理者宛の送る／送らないは §8.1 の設定による。送らない設定でも操作ログには記録する。

管理者宛の通知は、**宛先を複数にした1通**で、宛先は BCC に入れて送る（管理者どうしにアドレスを見せない。宛先欄には既定差出人を入れる）。管理者の人数分を1通ずつ送ることはしない。攻撃者が複数のアカウントをロックさせた時に、送信待ちでワーカーが塞がるのを抑えるため。

- **IP 遮断通知の条件の理由**：IP 遮断は専用の状態を持たない。遮断中の試行は失敗に数えないため件数は閾値で止まり、古い失敗が15分の枠から外れるたびに「再び閾値に達する」ことが起きる。件数だけで判定すると、攻撃が続く間に15分で最大20通の通知が出る。
- **宛先が0名の場合**：管理者宛の通知は送れない。操作ログには記録し、セキュリティ設定画面に「通知を受け取れる管理者がいません」と警告を表示する（§8.1）。

### 5.6 ログイン試行記録

- すべての試行（成功・失敗・拒否）を「ログイン試行記録」に1件ずつ残す。パスワードそのものは記録しない。
- **失敗・拒否の記録は、その後の処理で例外が起きても残る**ようにする（記録を、後で巻き戻される処理のまとまりの中に入れない）。
- 「第二要素の方法」は、第二要素まで進んだ行にだけ入れる。パスワード失敗・ロック中拒否・IP 遮断拒否の行は空にする（「未設定」は、二段階認証を登録していないユーザーが成功した行に使う）。
- **入力ユーザー名は先頭150文字までを保存する**（ユーザー名の最大長と同じ）。利用者が欄を取り違えてパスワードをユーザー名欄に入力すると、その文字列が記録と一覧画面に残る。一覧画面にこの性質を注記し、閲覧権限は管理者に限る（§11）。
- 用途：IP 遮断の判定、管理者向け一覧画面（§10）、本人向け「最近のログイン」表示（プロフィール画面に直近5件）。
- 保存期間は180日。超過分は管理コマンド（§12.2）を cron で1日1回実行して削除する。

### 5.7 接続元 IP の取得

本番は Cloudflare Tunnel 経由と LAN 直アクセスを併用している。**入口を nginx に一本化**し、接続元の補正は nginx で行う。Django は nginx が付ける `X-Real-IP` だけを読む。

| 構成 | nginx から見た接続元 | nginx の補正設定 | 記録される IP |
| --- | --- | --- | --- |
| LAN 直のみ（Cloudflare なし） | 利用者の端末 | 不要 | 利用者の IP |
| Cloudflare 経由 | cloudflared コンテナ | 必要 | 補正後の利用者の IP |
| 併用（現在の本番） | 経路により両方 | 必要 | どちらも利用者の IP |

- **トンネルの転送先は nginx の 443 番（https）にする**。nginx の 80 番は HTTPS へのリダイレクトだけを返すため、80 番を指定してはならない。nginx の証明書は自己署名のため、トンネル側で証明書検証を省略する設定が必要。転送先は LAN アドレスではなく nginx のコンテナ名で指定する（LAN アドレス経由だと、nginx から見た接続元が cloudflared の IP にならない）。
- **本番（g.freegroup.work）は確認済み**（2026-11-17）：転送先は nginx のコンテナ名・443 番で、変更不要。
- デモ用のホスト名（demo2.freegroup.work）は LAN アドレス経由の転送になっている。デモ環境へ本機能を入れる場合は、転送先の指定を本番と同じ形に揃える。
- **標準の nginx 設定には補正を書かない**。「追加設定フォルダがあれば読み込む」1行だけを入れる。フォルダが空でもエラーにならない。
- **Cloudflare を使う導入先だけ**、追加設定フォルダに補正用の設定ファイルを置く（リポジトリにサンプルを同梱）。内容は「cloudflared からの接続に限り、Cloudflare が付ける接続元ヘッダを採用する」。
- **信頼する接続元は cloudflared コンテナの IP だけに絞る**。そのため cloudflared コンテナに固定 IP を割り当てる（使う導入先だけの docker-compose 設定）。Docker のネットワーク全体を信頼すると、LAN からの通信が Docker のゲートウェイ IP に見える構成で、LAN の利用者がヘッダを偽装できる。
- 導入先が別の中継装置（社内のリバースプロキシ・ロードバランサー）を前段に置く場合も、同じ追加設定フォルダで対応する。
- **nginx を通さない環境**（Windows の開発環境など）は `X-Real-IP` が付かない。`.env` の「接続元 IP の取得元」を切り替えて、接続元をそのまま使う。初期値は Docker 構成向け（`X-Real-IP` を読む）。
- **誤設定の警告**：デバッグが無効（本番相当）なのに取得元が「接続元をそのまま使う」になっている場合、起動時のチェックで警告を出す。Docker 本番でこの設定にすると全員が nginx の IP になり、1人の失敗で全員が IP 遮断される。
- IP が取得できない・形式が不正な場合は空として記録する。その試行は IP 遮断の判定対象にならない（アカウントロックは働く）。

## 6. 二段階認証

### 6.1 方式

| 項目 | 仕様 |
| --- | --- |
| 第二要素 | 認証アプリ（TOTP）。Google Authenticator・Microsoft Authenticator 等の一般的なアプリで使える設定（6桁・30秒・SHA-1）とする |
| 時刻のずれ許容 | 前後1ステップ（±30秒） |
| 再利用防止 | 一度通ったコードは、同じ時間枠内でも二度目は拒否する。拒否時の扱いは下記「使用済みコードの扱い」 |
| 登録数 | 確定済みの登録は1ユーザーにつき1件。再登録中に限り、未確定の登録を別に1件持てる（§6.2） |
| 予備手段 | リカバリーコード（§6.3） |

サーバーの時刻がずれると全員が通らなくなる。本番サーバーの時刻同期（NTP）を運用前提とする。

**使用済みコードの扱い**（ログイン時の第二要素入力と、重要操作 §6.11 で共通）

- 入力されたコードが「正しいが使用済み」の場合は、失敗に数えず、専用の文言「このコードは使用済みです。認証アプリに次のコードが表示されるまでお待ちください。」を表示する。ログイン時は仮認証を維持する。
- ログアウト直後（30秒以内）の再ログインや、ログイン直後の重要操作で、正規の利用者に必ず起きるため。誤りと同じ扱いにすると、正規の利用者の失敗回数が増える。
- **判別方法**：django-otp の検証は「誤り」と「使用済み」を区別せず、不合格を返すだけである。検証が不合格だった時に、再利用防止の条件を外してもう一度照合し、それなら通る場合を「使用済み」と判定する。
- 使用済みと判定しても、ログインや操作は通さない（文言を変えて失敗に数えないだけ）。

### 6.2 登録フロー（本人操作）

1. プロフィール画面 →「二段階認証の設定」→「登録を開始」。
2. QR コードと、手入力用の秘密鍵（文字列）を表示する。**QR コードはサーバー内で生成する**（§14-6）。認証アプリに表示される発行者名は「FreeGroup2」を初期値とし、`.env` で変更できる（導入先の名前に変えられる）。
3. 認証アプリに表示された6桁コードを入力して確認する。正しければ登録確定。確定前の登録は第二要素として扱わない。
4. リカバリーコード10個を**この1回だけ**表示する。「保存しました」にチェックしないと完了できない。
5. 本人に「二段階認証を有効化しました」メールを送る。

再登録（機種変更）は、現在のコードまたはリカバリーコードを通したうえで、登録フローをやり直す。再登録が確定した時点で旧登録・旧リカバリーコード・端末の信頼をすべて無効化し、操作中のセッション以外を切断する（§6.10）。

- **再登録中は旧登録を消さない**。新しい登録は未確定のまま旧登録と別に持ち、確認コードが通った時点で旧登録と置き換える。旧登録を先に消すと、確認コードが通らなかった場合に二段階認証が外れた状態になる。
- 未確定のまま放置された登録は第二要素として扱わない。作成から24時間を超えた未確定の登録は、定期削除のコマンドで削除する（§12.2）。

### 6.3 リカバリーコード

| 項目 | 仕様 |
| --- | --- |
| 個数・形式 | 10個。1個は英数字10桁（読み間違えやすい文字 0/O・1/l/I は除外）、5桁ごとにハイフン区切りで表示 |
| 保存 | **サーバーの秘密鍵を使った鍵付きハッシュ（HMAC-SHA256）で保存**（平文で DB に置かない。パスワード用のハッシュ方式は使わない）。アルゴリズムは SHA-256 を明示的に指定する（指定しないと古い方式になる）。再表示は不可 |
| 照合 | 入力からハイフンと空白を除き、大文字にそろえてから鍵付きハッシュを計算し、**そのユーザーの未使用のコードの中で**ハッシュ値を検索する（ユーザーで絞らないと他人のコードで通る。全件を取り出して1個ずつ照合する方式は使わない） |
| 秘密鍵の入れ替え | 照合時は、現在の秘密鍵と、設定に残してある旧鍵のそれぞれでハッシュを計算して検索する。旧鍵を残している間は、鍵の入れ替え後も発行済みのコードが使える。旧鍵を設定から外すと、その鍵で発行したコードは無効になる（再発行を案内する） |
| 使用 | 第二要素入力画面で認証アプリのコードの代わりに入力。**1個1回限り** |
| 使用時の通知 | 本人に「リカバリーコードが使用されました（残り n 個）」メール |
| 残数の表示 | 二段階認証の設定画面に残数を表示。残り3個以下で警告表示 |
| 再発行 | 本人が設定画面から実行（現在のコードの入力が必要）。旧コードは全て無効。本人にメール通知 |

### 6.4 第二要素が必要かの判定（§4 順4）

| 状態 | 判定 |
| --- | --- |
| 認証アプリ登録なし | 不要（必須対象なら順11で登録へ誘導） |
| 登録あり、かつ有効な信頼済み端末（§6.6） | 省略（試行記録に「省略」と残す） |
| 登録あり、上記以外 | 必要 |

信頼済み端末かどうかの照合は、端末記録を更新する**前**に行う（§4 順4）。更新を先に行うと、初めての端末が既知の端末として扱われる。

### 6.5 強制レベル

「セキュリティ設定．二段階認証強制レベル」で決まる。

| 値 | 必須になる対象 |
| --- | --- |
| 任意（初期値） | なし。各自の判断で登録 |
| 管理者のみ必須 | 管理者ロール保持者、スーパーユーザー、Django 管理画面に入れるユーザー（スタッフ権限） |
| 全員必須 | 有効な全ユーザー |

- **強制誘導**：必須対象で未登録のユーザーは、ログイン成立後、登録画面・ログアウト・静的ファイル以外のすべての画面（Django 管理画面を含む）から登録画面へリダイレクトする。全リクエストで判定する（ログイン直後だけでは、レベル変更時にログイン中だったユーザーが抜ける）。
- **登録に使う画面は、ログイン済みであれば業務ロール・権限グループを一切問わず開ける**（認証アプリ登録・リカバリーコード表示・ログアウト）。業務権限を持たないスタッフ権限だけのユーザーも必須対象になるため、権限を要求すると登録できずに詰む。
- **強制誘導の実装位置**：全リクエスト共通の処理（ミドルウェア）として、認証の処理の後に置く。GET・POST・非同期リクエストのいずれも、登録画面へのリダイレクトで応答する。
- **強制誘導の除外先**：認証アプリ登録、リカバリーコード表示、ログアウト、Django 管理画面のログアウト、静的ファイル。
- **本人による無効化**：必須対象でない場合のみ可能。現在のコードの入力が必要。本人にメール通知。操作中のセッション以外を切断する（§6.10）。
- **レベルを上げた時**：ログイン中の未登録ユーザーは次の画面遷移で登録画面へ誘導される。設定した管理者自身も対象。
- **ユーザー個別の必須・免除の設定は設けない**。全員必須の導入先でスマートフォンを使えないユーザーには、PC 用の認証アプリを案内する運用とする。
- 任意レベルの導入先でも、本人が自分の判断で登録することはできる。

### 6.6 信頼済み端末

- 第二要素入力画面に「この端末を n 日間信頼する」チェックを置く（n は「セキュリティ設定．信頼期間（日）」、初期値30、0で機能自体を無効、設定可能範囲0〜90）。
- チェックして第二要素を通過すると、その端末の「端末記録．二段階認証省略期限」に期限を入れる。期限内は第二要素を省略する。
- 端末の識別は端末識別クッキー（§7.2）で行う。
- 本人は設定画面の端末一覧で、信頼の取り消し・端末記録の削除ができる。
- **信頼が一括で無効になる時**：本人による再登録・無効化、管理者リセット、信頼期間を0に変更した時、**パスワードリセットの完了時**（パスワード仕様書 §6.5。パスワードを忘れた状況は漏洩の疑いを含むため）。
- 省略中でもパスワード（第一要素）は毎回必要。省略されるのは第二要素だけ。

### 6.7 管理者によるリセット

| 項目 | 仕様 |
| --- | --- |
| 操作者 | 権限「二段階認証リセット」保持者（初期状態では管理者ロール） |
| 入口 | ユーザー詳細画面 →「二段階認証をリセット」→ 確認画面 → 実行 |
| 自分自身 | 対象にできない（本人は §6.2 の再登録を使う） |
| 対象が管理者 | 可能（管理者同士で復旧できることが「2名以上推奨」の目的） |
| 実行内容 | 認証アプリ登録・リカバリーコード・端末の信頼を削除。アカウントロックも解除。**対象ユーザーの全セッションを切断**（§6.10）。パスワードは変更しない |
| 記録 | 操作ログに記録（操作者・対象・理由メモ） |
| 通知 | 対象ユーザー本人 ＋ 管理者全員 |
| 本人確認 | FG2 の外（電話・対面）で行う運用。確認画面にその旨を表示 |
| 実行のタイミング | 確認画面に「本人がすぐに登録操作を行える状態で実行してください。実行後は、本人に速やかに登録を完了してもらってください」と表示する |

リセット後、対象ユーザーはパスワード（または LDAP 認証）だけでログインでき、必須対象ならそのまま登録画面へ強制誘導される（§6.5）。

リセットから再登録までの間は、パスワードを知る者なら誰でも自分の認証アプリを登録できる。パスワードが漏れている場合は、本人より先に攻撃者が登録できてしまう。リセットの性質上避けられない弱点のため、上記の表示と本人宛通知メールで、空白の時間を短くする運用とする。

### 6.8 管理者が全員締め出された場合

サーバーに入れる者が、管理コマンド「二段階認証リセット」（§12.2）で管理者1名を復旧する。

| 順 | 内容 |
| --- | --- |
| 1 | サーバー上でコマンドを実行（対象の管理者のユーザー名を指定）。実行内容は §6.7 と同じ。パスワードは変わらない |
| 2 | 本人と管理者全員に通知メール。操作ログには操作者なし（コマンド実行）として記録 |
| 3 | 本人がパスワード（LDAP ユーザーは LDAP 認証）だけでログイン |
| 4 | 必須対象なら登録画面へ強制誘導され、認証アプリを登録し直す |
| 5 | 残りの管理者は、復旧した管理者が画面からリセットする（§6.7） |

| 提供形態 | コマンドを実行する者 | 実行前の本人確認 |
| --- | --- | --- |
| 導入先が自社サーバーで運用 | 導入先でサーバーに入れる者 | 不要（サーバーに入れることを本人確認の代わりとみなす） |
| ディストリビュータが運用 | ディストリビュータ | 必要（付録B の手順案） |
| SaaS 直販 | ネットワーク東海 | 必要（付録B の手順案） |

- **パスワードも忘れている場合**：本コマンドでは復旧できない。ローカルユーザーは、本コマンドで二段階認証をリセットした後、**本人がメール経由でパスワードを再設定**できる（パスワード仕様書 §6.7。従来は Django 標準のパスワード変更コマンドとの併用が必要だった。同コマンドは運用ツールとして残る）。LDAP ユーザーは導入先の LDAP 側で再設定する。
- **マルチテナント化した場合**：現コマンドはユーザー名だけを指定する。テナントが複数になる時は、対象テナントも指定できるよう拡張する（SaaS 化の設計時に対応、§17-2）。

### 6.9 管理者2名以上の推奨

有効な管理者（管理者ロール保持者とスーパーユーザー。§5.5 の「管理者全員」と同じ範囲でメールアドレスの有無は問わない）が1名以下のとき、セキュリティ設定画面とユーザー一覧画面に警告を表示する（「管理者が1名です。二段階認証の端末を紛失すると復旧できなくなるため、2名以上を推奨します」）。強制はしない。

### 6.10 セッション切断

| 場面 | 切断する範囲 |
| --- | --- |
| 管理者による二段階認証リセット（画面・コマンド） | 対象ユーザーの全セッション |
| 本人による再登録の確定 | 本人のセッションのうち、操作中のもの以外 |
| 本人による無効化 | 同上 |

- 目的：第二要素を入れ替える・外す時点で、盗まれたセッションや置き忘れた端末のログイン状態を残さない。
- Django のセッション表にはユーザーの列がないため、有効期限内のセッションを1件ずつ復号し、対象ユーザーのものを削除する。FG2 の利用規模では負荷は問題にならない。
- アカウントロック発生時はセッションを切らない（ログイン中の正規ユーザーを巻き込まないため）。

### 6.11 重要操作でのコード入力

無効化（§6.5）、リカバリーコードの再発行（§6.3）、再登録の開始（§6.2）では、現在のコード（認証アプリまたはリカバリーコード）の入力を求める。この入力の扱いはログイン時と同じにする。

| 項目 | 仕様 |
| --- | --- |
| 失敗の扱い | **ログイン時と同じ連続失敗回数に加算**する（§5.1）。閾値に達すればアカウントロックに入り、通知も同じ |
| ロック中 | 操作を拒否する（ログイン済みのセッションはそのまま） |
| 試行記録 | ログイン試行記録に「コード失敗」として残す |
| 直前に使ったコード | 失敗に数えず、専用の文言を表示する（§6.1「使用済みコードの扱い」。ログイン時と共通） |

加算しないと、盗まれたセッションから6桁のコードを無制限に試され、二段階認証の無効化まで到達できてしまう。

## 7. ログイン通知メール

### 7.1 通知レベル

「セキュリティ設定．ログイン通知レベル」で決まる。

| 値 | 送る条件 |
| --- | --- |
| 毎回（初期値） | すべてのログイン成功 |
| 新しい端末のみ | 新しい端末（§7.2）からのログイン成功のみ |

どちらの値でも、新しい端末からのログインは必ず通知される。件名で区別する。

| 場合 | 件名 |
| --- | --- |
| 既知の端末 | 【FreeGroup2】ログイン通知 |
| 新しい端末 | 【FreeGroup2】【要確認】新しい端末からのログイン |

### 7.2 新しい端末の判定

- ログイン成立時に端末識別クッキー（ランダムなトークン。有効1年、ログインのたびに延長）を発行し、そのハッシュを「端末記録」に保存する。
- **クッキーの名前は環境ごとに変えられるようにする**（`.env` で指定。初期値は既存のセッションクッキーと同じ流儀で接尾辞を付けた名前）。同じホストの別ポートで複数の FG2 を動かした時に、端末記録が混ざるのを防ぐ。
- 端末トークンは十分に長いランダム値のため、保存するハッシュは通常の SHA-256 でよい（リカバリーコードと違い、鍵付きである必要はない）。
- ログイン時にクッキーがない、または当該ユーザーの端末記録と一致しなければ「新しい端末」とする。
- 二段階認証を登録していないユーザーにも端末記録は作る（通知の判定に必要なため）。
- クッキーを消す・別ブラウザを使う・シークレットウィンドウを使うと新しい端末扱いになる（仕様）。

### 7.3 本文の項目

宛先は本人（ユーザー．メールアドレス）。差出人は既定差出人。

| 項目 | 内容 |
| --- | --- |
| ログイン日時 | 日本時間 |
| ユーザー名 | — |
| IP アドレス | §14-5 の取得関数による |
| ブラウザ・OS | ブラウザ情報から要約（例：Chrome／Windows） |
| 第二要素 | 認証アプリ／リカバリーコード／省略（信頼済み端末）／未設定 |
| 心当たりがない場合 | パスワード変更と管理者への連絡を促す文言 |

フィッシング対策として、本文にログイン用のリンクは入れない。

### 7.4 送信の扱い

- 同期送信とする。通知メールは**共通のメール送信部品（§7.6）**で送り、**送信タイムアウトは5秒**を指定する（メール配信機能の送信設定には影響させない）。
- **送信に失敗してもログインは成立させる**。失敗はエラーログに残す（共通部品が記録する）。
- 送信は DB の確定後に行う。管理者宛は宛先を複数にした1通で送る（§5.5）。
- メールアドレスが空のユーザーには送れない。ユーザー一覧に「通知先なし」と表示して管理者が気づけるようにする。
- SMTP が未設定（既定差出人が空）の場合、セキュリティ設定画面に警告を表示する。

### 7.5 通知メール一覧（本仕様書全体）

| 事象 | 本人 | 管理者全員 | 通知レベルの影響 |
| --- | --- | --- | --- |
| ログイン成功 | ○ | — | 受ける |
| アカウントロック発生 | ○（常に送る） | △（§8.1 の設定で送らないにできる） | 受けない |
| IP 遮断発生 | — | △（同上） | 受けない |
| 二段階認証の有効化・無効化・再登録 | ○ | — | 受けない |
| リカバリーコードの使用・再発行 | ○ | — | 受けない |
| 管理者による二段階認証リセット | ○ | ○ | 受けない |
| セキュリティ設定を弱める変更（§8.2） | — | ○ | 受けない |

○＝常に送る（設定で止められない）。設定値を変えただけ（弱める変更に当たらないもの）では、一般ユーザーへの通知は行わない。

### 7.6 共通のメール送信部品（v1.3.2 で新設）

FG2 の送信処理はメール配信（キャンペーン）専用の1か所だけで、ほかの機能から使える送信関数がない（§3）。本機能の通知メールのために、**どの機能からも使える送信部品を新設**する。見積書DB（v1.9）の見積送付・受注通知・Web 発注の受付メールでも同じ部品を使う。

| 項目 | 仕様 |
| --- | --- |
| 置き場所 | 共通部品用のパッケージ。モデルを持たないため Django アプリとしては登録しない |
| 受け取るもの | 宛先（To）、BCC、件名、本文（テキスト）、添付ファイル（任意。ファイル名・内容・形式の組を複数）、差出人（省略時は既定差出人）、タイムアウト秒数（省略時は既定値） |
| 本文 | テキストのみ。HTML メールは扱わない（必要になった時に拡張する） |
| 接続 | 呼び出しのたびに、指定したタイムアウトを持つ専用の接続を作る。メール配信機能の接続・送信設定は使わない |
| 結果 | **例外を外に出さず、成否を真偽で返す**。失敗時はエラーログに、宛先の件数・件名・例外の種類を残す（宛先のアドレス・本文・添付は出力しない） |
| 宛先の検査 | 空文字のアドレスは除く。宛先と BCC がすべて空になったら送信せず、偽を返す |
| DB との関係 | 部品自体はトランザクションを扱わない。**DB の確定後に送るのは呼び出し側の責任**とし、確定後に実行する仕組みから呼ぶ |
| メール配信機能 | 既存の配信の送信処理には手を入れない。配信は従来どおり専用の処理で送る |

- タイムアウトの既定値は `.env` で変えられるようにする（初期値10秒）。本機能の通知は常に5秒を明示して呼ぶ。
- 管理者宛の1通にまとめた通知（§5.5）は、宛先欄に既定差出人、管理者を BCC に入れて1回呼ぶ。
- 失敗を真偽で返すのは、呼び出し側ごとに扱いが違うため。本機能は失敗してもログインを通し、見積書DB の見積送付では画面にエラーを表示する。
- **実装の場所（v1.3.3）**：本部品は、二段階認証のブランチ（feature/two-factor-login）には実装されていない（通知は専用の送信処理で送っている）。**パスワード仕様書のブランチ（Step 1）で新設**し、二段階認証の通知の載せ替えは同ブランチの最後（Step 6）に別コミットで行う。載せ替えでは、通知の内容・宛先・タイミング・5秒のタイムアウトを変えない。

## 8. セキュリティ設定画面

### 8.1 設定項目

「セキュリティ設定」モデルはシングルトン（メール配信設定と同じ方式）。権限「セキュリティ設定管理」保持者のみ変更できる。

| フィールド（完全修飾名） | 初期値 | 選択肢・範囲 |
| --- | --- | --- |
| セキュリティ設定．二段階認証強制レベル | 任意 | 任意／管理者のみ必須／全員必須 |
| セキュリティ設定．ログイン通知レベル | 毎回 | 毎回／新しい端末のみ |
| セキュリティ設定．ロック失敗回数 | 5 | 3〜10 |
| セキュリティ設定．ロック時間（分） | 15 | 5〜1440 |
| セキュリティ設定．IP遮断失敗回数 | 20 | 10〜100 |
| セキュリティ設定．信頼期間（日） | 30 | 0〜90（0＝信頼済み端末を使わない） |
| セキュリティ設定．ロック発生を管理者に通知 | 送る | 送る／送らない |
| セキュリティ設定．IP遮断を管理者に通知 | 送る | 送る／送らない |

数値の初期値は v1.1 で確定。管理者宛通知のうち、二段階認証リセットと「弱める変更」は設定項目を持たず、常に送る。

画面には現在の状況（二段階認証の登録済み人数／有効ユーザー数、ロック中の人数、管理者人数の警告、通知を受け取れる管理者が0名の警告、SMTP 未設定の警告）も表示する。

### 8.2 変更時の扱い

- すべての変更を操作ログに記録する（変更前後の値）。
- **弱める変更**は管理者全員にメール通知する。弱める変更の定義：強制レベルを下げる／通知レベルを「毎回」から「新しい端末のみ」へ／ロック失敗回数を増やす／ロック時間を短くする／IP遮断失敗回数を増やす／信頼期間を延ばす／管理者宛通知（ロック発生・IP 遮断）を「送らない」にする。
- 乗っ取られた管理者アカウントが設定を緩めたことに、他の管理者が気づけるようにするため。

## 12. 操作ログ・管理コマンド

### 12.1 操作ログに記録する事象

操作ログの記録対象は仕様書で明示する決まりのため、ここに列挙したものだけを記録する。ログイン成功・失敗は操作ログではなくログイン試行記録に残す。

アクション値（付録A）は、既存の操作ログ定数クラス（accounts アプリの定数ファイル）に追加する。

既存の操作ログ記録処理への渡し方：変更前後の値・IP アドレスなどは「追加情報」欄に、理由メモは「補足メモ」欄に入れる。システムによる記録（ロック発生・IP 遮断・コマンド実行）は操作者を空にする（既存の記録処理は操作者なしを受け付ける）。

| 事象 | 操作者 | 対象 |
| --- | --- | --- |
| セキュリティ設定の変更 | 管理者 | セキュリティ設定（変更前後の値） |
| 二段階認証の有効化／無効化／再登録 | 本人 | 本人 |
| リカバリーコードの再発行 | 本人 | 本人 |
| 管理者による二段階認証リセット | 管理者（コマンド時は空） | 対象ユーザー（理由メモ） |
| アカウントロック発生 | 空（システム） | 対象ユーザー（IP） |
| ロックの手動解除 | 管理者（コマンド時は空） | 対象ユーザー |
| IP 遮断発生 | 空（システム） | なし（IP を記録） |
| 端末の信頼取り消し・削除 | 本人 | 本人 |

秘密鍵・リカバリーコード・端末トークンは、操作ログにもエラーログにも出力しない。

## 13. Django 管理画面の扱い

- `/admin/login/` は独自の認証をさせず、共通のログイン画面（#1）へリダイレクトする。ログイン成立後に管理画面へ戻す。
- 管理画面も強制誘導（§6.5）の対象に含める。
- 強制誘導は全リクエスト共通の処理（ミドルウェア）で行うため、必須対象で未登録のユーザーが `/admin/` へ直接アクセスしても、**管理画面側の権限チェックより先に**登録画面へ誘導される。
- 管理画面に、TOTP 端末・リカバリーコード・端末記録を**編集できる形で登録しない**（秘密鍵の閲覧や、リセット手順を迂回した削除を防ぐ）。ログイン試行記録とアカウントロックは閲覧専用で登録してよい。

## 14. 実装上の厳守事項（踏み外しやすい点）

| # | 厳守事項 | 破ると起きること |
| --- | --- | --- |
| 1 | 第一要素が通っただけでログイン済みにしない。セッション確立は第二要素の成功後（§4 順7） | 第二要素入力画面を飛ばして他の URL に直接入れる |
| 2 | 仮認証状態には、ユーザー・通過した認証バックエンド・開始時刻・遷移先だけを持つ。5分で失効。セッション確立時に認証バックエンドを明示して渡す | LDAP ユーザーでセッション確立に失敗する／仮認証が無期限に残る |
| 3 | 連続失敗回数を0に戻すのはログイン完全成立時のみ。第一要素の成功では戻さない | パスワードを知る攻撃者が、パスワード再入力のたびにコードを5回試せる（6桁の総当たりが可能になる） |
| 4 | 失敗回数・ロックは DB に置く。加算は **DB 側の加算式**で行い、数え直しと加算は1回の更新にまとめ、ロックの開始は条件付きの更新で判定する（§5.4）。読み出してから保存する方式・行ロック頼みの方式は使わない | 3ワーカー間で回数が共有されず実質15回以上試せる／SQLite と PostgreSQL で挙動が変わる／ロック通知が重複する |
| 5 | 接続元 IP は専用の取得関数1か所で取る。関数は nginx が付ける `X-Real-IP` だけを読み、クライアントが送ってきた転送ヘッダ（Cloudflare の接続元ヘッダを含む）を Django 側で読まない。Cloudflare 経由の補正は nginx で行う（§5.7）。既存の `REMOTE_ADDR` 直読みを真似しない | 全員が nginx や cloudflared の IP になり、1人の失敗で全社が IP 遮断される／LAN から IP を偽装される |
| 6 | QR コードはサーバー内で生成する。外部の QR 生成サービス・外部スクリプトを使わない | 秘密鍵が外部に送信される |
| 7 | ロック判定は認証処理の**前**に行う（§4 順2）。ロック中は LDAP バインドを発生させない | FG2 経由で AD アカウントがロックされる |
| 8 | 認証処理とセッション確立を呼ぶ場所は共通のログインサービス1か所に限定する。管理画面ログインも同じ経路へ寄せる（§13） | 二段階認証を通らない入口が残る |
| 9 | パスワードリセット機能は、**別仕様書「パスワード変更・リセット 仕様書」で実装する**（同仕様書 §6.5・§13-1 で具体化）。いずれにせよ、リセット完了で自動ログインさせない。二段階認証の登録も解除しない | メール乗っ取りで第二要素ごと突破される（決定 #6 が無意味になる） |
| 10 | 画面のエラー文言は §4 の共通エラー表示に統一する | ユーザー名の存在やロック状態が外部から判別できる |
| 11 | 通知メールの送信失敗でログインを失敗させない。送信は DB の確定後に行う。通知メールは**共通のメール送信部品（§7.6。実装はパスワード仕様書のブランチ）**で、5秒のタイムアウトを指定して送り、管理者宛は1通にまとめる。**メール配信機能の送信処理を流用しない** | SMTP 障害で全員がログインできなくなる／送信待ちで3ワーカーが塞がる／配信専用の処理（差出人の差し替えなど）が通知メールに混ざる |
| 12 | リカバリーコード・端末トークンは平文で保存しない。リカバリーコードは鍵付きハッシュ、端末トークンは SHA-256 で保存し、ハッシュ値で直接検索する。**リカバリーコードの検索は、必ず対象ユーザーの未使用のコードに絞る**。鍵付きハッシュのアルゴリズムは SHA-256 を明示する。リカバリーコードにパスワード用のハッシュ方式を使わない | DB 漏洩時にそのまま使われる／他人のリカバリーコードでログインできる／照合に数秒かかり、連打でワーカーが塞がる |
| 13 | django-otp 側の失敗時待機機能は無効にし、ロックは FG2 側（§5）に一本化する | 二重のロックが働き、解除したのに通らない状態になる |
| 14 | 端末識別クッキーは HttpOnly と SameSite を常に付ける。**Secure はリクエストが https の時だけ付ける**（既存のプロキシ経由 https 判定に従う） | HttpOnly がないとスクリプトから盗まれる。Secure を常に付けると、http の開発環境でクッキーが戻らず、毎回「新しい端末」になり信頼済み端末も機能しない |
| 15 | **本機能のコードはユーザー本体（ユーザーモデル）を保存せず、ユーザーモデルにフィールドも足さない**。失敗回数・ロック・端末・試行記録はすべて別モデルに持つ。Django 標準の最終ログイン日時の更新、LDAP 認証時の保存（既存挙動、§3）、パスワードのハッシュ方式の自動更新は対象外。**パスワード変更・リセット（別仕様書）によるパスワードだけの保存（保存するフィールドをパスワードに限る）も対象外** | LDAP ログインでは全項目が保存し直されるため、ユーザーモデルに置いた失敗回数が古い値で上書きされる。AccessList 再実装後は、保存のたびに余計な問い合わせが増える（§18） |
| 16 | セッション切断は、対象ユーザーのセッションだけを消す。本人操作の場合は操作中のセッションを残す。全ユーザーのセッションを消す実装にしない | 全員が強制ログアウトされる／操作した本人が画面から追い出される |
| 17 | django-otp は秘密鍵の保管とコード検証にだけ使う。django-otp のミドルウェアを登録しない。付属の「第二要素を通ったか」の判定機能・判定用デコレーターを使わない | リカバリーコードや信頼済み端末での正規ログインが「未通過」と判定され、画面に入れなくなる |
| 18 | 第二要素の検証の直前にも、IP 遮断とアカウントロックを判定する（§4 順6）。かかった場合は仮認証を破棄する | ロック中でもコードの総当たりを続けられる |
| 19 | 再登録では旧登録を先に消さない。新しい登録が確定した時点で置き換える（§6.2） | 確認コードが通らなかった時に二段階認証が外れる |
| 20 | 認証アプリ登録・リカバリーコード表示・ログアウトは、ログイン済みであれば権限を問わず開けるようにする。強制誘導の除外先にも含める | 業務権限のないスタッフ権限ユーザーが登録できず、リダイレクトが循環する |
| 21 | ロックの判定と失敗の加算では、§5.1 の規則（空白除去・大文字小文字を区別しない）でユーザーを特定する。認証バックエンドの照合とは別に、共通の関数1か所で行う | LDAP ユーザーに対し、大文字小文字を変えるだけでロックを回避できる |
| 22 | 重要操作（無効化・再発行・再登録）でのコード失敗も、ログイン時と同じ失敗回数に加算する。ロック中は操作を拒否する（§6.11） | 盗まれたセッションから6桁を無制限に試され、二段階認証を無効化される |
| 23 | 認証アプリ登録の検索は、必ず「確定済み」を条件に付ける。1ユーザー1件を前提にした取得をしない | 再登録中は確定済みと未確定の2件があり、1件前提の取得は例外で落ちる／未確定の登録が第二要素として通る |
| 24 | 使用済みコードは、検証が不合格だった後に、再利用防止の条件を外した照合で判別する（§6.1）。使用済みと判定してもログイン・操作は通さない。判別のための照合で、登録側の「最後に使った位置」を書き換えない | 正規の利用者の失敗回数が増える／判別用の照合が再利用防止を壊し、同じコードが二度通る |

## 15. テスト観点

DB の読み書き結果が変わるロジックのため、テストを実行する（UI 文言・レイアウトのみの変更は対象外）。

| 分類 | 確認すること |
| --- | --- |
| フロー | 第一要素のみ通過した状態で他の画面に入れない／仮認証が5分で失効する／LDAP・ローカル両方で第二要素後にログインが成立する／仮認証中にロック・IP 遮断に入ると検証されず仮認証が破棄される |
| ロック | 閾値でロックされる／ロック中は正しいパスワードでも拒否される／ロック中は認証処理が呼ばれない／時間経過で自動解除される／コード失敗も加算される／第一要素成功では回数が戻らない／完全成立で0に戻る／大文字小文字や前後の空白を変えてもロックが効き、失敗が同じユーザーに加算される |
| IP 遮断 | 閾値で遮断される／15分経過で解除される／存在しないユーザー名への試行も数える |
| 二段階認証 | 未確定の登録は第二要素にならない／同じコードの再利用が拒否される／リカバリーコードは1回限り／ハイフンの有無・大文字小文字が違っても通る／他人のリカバリーコードは通らない／旧鍵で発行したコードが、旧鍵を設定に残している間は通る／使用済みコードは通らず、失敗に数えられず、専用文言になる（ログイン時・重要操作とも）／再発行で旧コードが無効になる／再登録の確認コードが通るまで旧登録が有効／確認失敗で旧登録が残る／未確定の登録が24時間で削除される |
| 信頼済み端末 | 期限内は省略される／期限切れ・取り消し・リセット後は要求される／信頼期間0で全員要求される |
| 強制 | 必須対象の未登録者が全画面から誘導される（管理画面含む）／業務権限のないスタッフ権限ユーザーが登録画面を開けて登録を完了できる／必須対象は無効化できない／レベル変更が即時に効く |
| リセット | 権限なしは拒否／自分自身は対象にできない／登録・コード・信頼・ロックが消える／パスワードは変わらない |
| セッション切断 | リセットで対象ユーザーの全セッションが切れる／他ユーザーのセッションは残る／再登録・無効化では操作中のセッションだけ残る |
| ユーザー保存 | ローカルユーザーのログイン失敗・ロック・第二要素の検証で、ユーザーモデルの保存が発生しない（LDAP 成功時の保存は既存挙動のため対象外） |
| 通知 | レベルごとの送信有無／新しい端末は常に送る／件名の区別／送信失敗でもログイン成立／ロック通知は1回だけ／管理者宛を「送らない」にしても本人宛ロック通知は届く／リセットと弱める変更の通知は止められない |
| 共通のメール送信部品 | 送信失敗で例外が外に出ず偽が返る／宛先と BCC がすべて空なら送らずに偽が返る／指定したタイムアウトで接続する／添付が付く／失敗時のエラーログに宛先のアドレス・本文が出ない／メール配信機能の送信が従来どおり動く |

## 18. AccessList 再実装時の申し送り

AccessList は本機能の完了後に、本機能を取り込んだ main の上で再実装する。その時に確認すること。

| 項目 | 内容 |
| --- | --- |
| マイグレーション番号 | accounts の 0018 以降は本機能が使用済み（0018・0019）。**パスワード仕様書が 0020 を使う**。AccessList 側のユーザーグループ追加（旧ブランチでは 0018）は、その後ろの **0021 以降**で作り直す |
| サイドバー | 本機能が「セキュリティ設定」「ログイン試行記録」を追加済み。AccessList の「アクセス管理」項目はその後に足す |
| URL・設定ファイル | 本機能が accounts の URL と、アプリ・ミドルウェアの登録を追加済み |
| 権限グループ | 本機能はユーザー管理者グループに権限3種（§11）を追加するだけで、グループ構成は変えていない |
| ユーザー保存時のシグナル | 旧ブランチは、ユーザー保存のたびに保存前の「有効・無効」と「部署」を読み直し、**変わっていた時だけ**再計算していた（最終ログイン日時だけの更新は読み直しも省略）。LDAP ログインではユーザーが毎回2回保存されるが（§3）、この方式なら変更のない保存で増えるのは問い合わせ1回で、再計算は走らない。**再実装時も「変更を検知してから再計算する」方式を維持すること**。保存のたびに無条件で再計算する作りにしてはならない |
| パスワードだけの保存（v1.3.3） | パスワード変更・リセット（パスワード仕様書）は、保存するフィールドをパスワードに限ってユーザーを保存する（§14-15）。旧 AccessList は「最終ログイン日時だけなら再計算を省く」条件だけのため、パスワードだけの保存でも読み直し1回が増える。**再計算を省く条件に、パスワードだけの保存（保存するフィールドをパスワードに限った保存）も加えることを推奨する** |
| 本機能とユーザー保存 | 本機能のコードはユーザー本体を保存せず、ユーザーモデルにフィールドも足していない（§14-15）。ログイン失敗やロックでシグナルが発火することはない |
| 新規モデルへの波及 | 本機能の5モデルはユーザーへの参照を持つだけで、AccessList の対象データ（案件・パーソン等）には関与しない |

| 1 | **契約時に復旧連絡先を登録**しておく：契約者の代表電話番号、復旧責任者2名の氏名とメールアドレス | 依頼を受ける相手を事前に固定する |
| 2 | 復旧依頼は**登録済みメールアドレスからのみ**受け付ける | 第三者からの依頼を入口で断る |
| 3 | 運営側から**登録済みの電話番号へ折り返して**依頼内容を確認する。依頼メールに書かれた番号は使わない | なりすまし対策の要 |
| 4 | 受付時点で、その導入先の管理者全員と復旧責任者に「リセット依頼を受け付けました」とメールし、**24時間待機**する。異議がなければ実行 | 本物の管理者が不正な依頼に気づいて止められる |
| 5 | 管理コマンドで**管理者1名分だけ**リセットする（§6.8）。残りは復旧した管理者が画面から行う | 運営側の操作範囲を最小にする |
| 6 | 受付日時・確認した相手・実行者・実行日時を運営側の記録に残す | 事後に追跡できるようにする |

**待機期間の省略**：急ぎの場合に限り、復旧責任者2名の両方に電話で確認が取れた時は24時間待機を省略できる、という条件を設ける案。
