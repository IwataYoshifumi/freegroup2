# FreeGroup2 Human Interface Guidelines
### 画面設計のよりどころ

> この文書は FreeGroup2（FG2）の画面設計の**よりどころ**です。
> 個々のルールの前に、なぜそうするのかという**原則**を置いています。
> 規約に載っていない場面に出会ったら、第1章の原則に立ち返って判断してください。
> クラス名・数値などの実装の具体は第6章（付録）にまとめてあります。

**対象読者**：FG2 の画面を作る人（コード君A／B、ジット君、たんたん）
**版**：v1.2（たたき台）
**最終更新**：2026-05-30

---

## 第1章 設計原則

FG2 の UI は、次の5つの原則を上位に置きます。個別のルールはすべてこの原則から導かれます。ルールと原則が食い違って見えたときは、原則を優先してください。

### 原則1 — 視線とポインタの移動を最小にする

ユーザーが目的を果たすまでに、目を動かす距離・マウスを動かす距離を可能な限り短くします。入力欄が画面いっぱいに広がっていると、ラベルと入力位置の間で視線が往復し、ポインタの移動も増えます。関連する操作は近くにまとめ、画面の横幅は内容に合わせて絞ります。

FG2 の利用者（たんたんを含む）には視覚的な負担を抱える人がいます。文字はやや太め・黒系で、背景とのコントラストを十分に確保します。「小さく・薄く・詰めて」より「読みやすく・はっきり」を選びます。

### 原則2 — 既存資産の上で完結させる

FG2 の見た目は `app.css` / `app.js`（BEM 風命名）で作られています。新しい画面も、原則としてこの既存のクラスとコンポーネントの組み合わせで作ります。新規 CSS/JS ファイルは作りません。

重要な前提として、**FG2 は Bootstrap5 本体 CSS を導入していません**。`base.html` が読み込むのは `bootstrap-icons.css`（アイコンフォント）だけです。`crispy-bootstrap5` はフォームの HTML を生成するためのもので、Bootstrap 本体 CSS の読み込みとは別物です。したがって素の `.btn` / `.btn-check` / `.btn-group` などの Bootstrap クラスは効きません。そして Bootstrap 本体を後から読み込むこともしません。本体を入れるとリセット CSS・タイポグラフィ・全コンポーネントが既存の `app-*` と干渉し、ボタン・テーブル・見出しなど全画面の見た目が一斉に変わるためです。Bootstrap "風" の見た目が欲しいときは、必要なものだけ `app.css` に自前で実装します。

**ただし FG2 は Bootstrap の作法から離れるわけではありません。** クラスの意味づけ（primary / secondary / success / warning / danger）、トグルの仕組み（隠し input ＋ label の着色）、コンポーネントの考え方は Bootstrap と同じ発想に揃えてあります。接頭辞が `app-` である点を除けば、Bootstrap に慣れた人はほとんど読み替えなしに理解し実装できます。FG2 が持たないのは Bootstrap への**依存**であって、その**作法**ではありません。

ここで一点、誤解を避けるための釘を刺しておきます。**Bootstrap と同型なのは、すでに `app.css` に実装済みの範囲だけです。** Bootstrap のドキュメントに載っているクラスが何でも使えるわけではありません。`app.css` に定義のない Bootstrap クラス（例：未実装のコンポーネント）は単に効きません。新しい部品が必要になったら、Bootstrap の作法を参考に `app.css` へ自前で足す ―― という順序を守ってください。「Bootstrap にあるから書けば動く」ではない、という点に注意。

### 原則3 — 状態と危険度を色で一貫して伝える

ボタンの色は装飾ではなく**意味**です。操作の安全度・危険度を、信号機のメタファーで一貫して表します。緑は安全な操作（編集・復旧など、データを壊さず後から見直せるもの）、黄は注意（やり直せる操作。アーカイブ化やマージ・復元など、影響はあるが取り消せるもの）、赤は危険（やり直せない操作。物理削除など）、青は主要な前向きの操作（新規作成など、ユーザーがその画面で起こしたい中心の行動）。この対応を全画面で揃えることで、ユーザーは色を見ただけで操作の重さを判断できます。色の割り当てを画面ごとに変えてはいけません。具体的なクラスと操作の対応は 3.6 の表を参照してください。

### 原則4 — 説明は隠し、必要な時だけ開く

入力欄ごとの補足説明を常に画面に並べると、情報量が増えて本来見るべき項目が埋もれます。説明は「?」アイコンやツールチップ、折りたたみの中にしまい、必要な時にその場で開ける形にします。普段の画面は、操作に必要な最小限だけが見えている状態を目指します。

なお、説明文そのものにシステム内部の表記（仕様書の章番号、rev 番号、`PROTECT` などの実装用語）を混ぜてはいけません。エンドユーザーに見える文面は、エンドユーザーの言葉で書きます。

### 原則5 — 操作には必ず応答を返す

ユーザーが何かをしたとき、あるいは画面を開いたときには、システムは必ず応答を返します。「押したのに何も起きない」「開いたら空っぽで、次に何をすればいいか分からない」という無反応の瞬間を作りません。

FG2 は中核に**すぐ結果が出ない処理**を抱えています。名刺取り込みの OCR は裏で時間をかけて動き（cron 非同期）、メール配信はバッチで走ります。ボタンを押した直後に画面が変わらないと、ユーザーは「効いたのか」が分からず同じボタンを押し直し、二重取り込み・二重送信という実害につながります。だからこそ、応答を返すことは色やレイアウトと同格の、FG2 の中核原則です。

応答には3つの場面があります。処理を受け付けたときに「進んでいる」と見せること、失敗したときに「次に何をすればいいか」を示すこと、まだ何もないときに「最初の一歩」を案内すること。具体は第5章で定めます。

## 第2章 レイアウト

> 原則1（視線・ポインタの移動を最小に）から導かれます。

### 2.1 コンテンツは画面中央に寄せる

編集・詳細を問わず、画面の主たるコンテンツは全幅まで広げず、**それを囲むカード枠（`app-card` 等）に `max-width` と中央寄せ（`margin: 0 auto`）をかけます**。大きなディスプレイでも内容が左に張り付かず、画面幅が変わっても情報の置かれる位置が一定になり、視線の起点が安定します（原則1）。

重要なのは、フォーム単体ではなく**外側のカード枠ごと幅を絞る**ことです。入力欄だけを絞ってカードが全幅のまま残ると、カードの中で入力欄が左に寄り、右側が間延びして見えます。カードごと中央に収めれば、中の要素も自然に収まります。

### 2.2 幅は内容に合わせる

`max-width` の目安は画面の性質に応じて決めます。縦1列が主体の編集フォームは狭め（`720〜800px` 程度）、情報量の多い詳細・閲覧画面は広めにします。編集と詳細で目安が違っても構いません ―― 用途が違うので、無理に揃えるより各画面が収まる幅を選びます。2カラム構成のときは、片方を固定幅帯（例：`minmax(320px, 420px)`）、もう片方を可変（`1fr`）にして、画面が広がっても要素が間延びしないようにします。

## 第3章 アクションとボタン

> 原則1（移動の最小化）と原則3（危険度を色で）から導かれます。

### 3.1 配置 — 主要は近く、破壊的は離す

画面の主要な操作ボタン（編集・送信・新規作成など）は**左寄せ**にまとめます。ユーザーの視線とポインタの起点に近い側に置くことで、迷わず手が届きます。

一方、**削除などの破壊的な操作だけは、同じ行の右端に分離**します。主要操作の隣に並べると誤クリックを誘発するため、意図的に距離を取ります。「離れた位置にある」こと自体が、誤操作を防ぐガードになります。

### 3.2 離脱の導線は「戻る」で統一

画面から離れる・操作を中断する導線のラベルは、**すべて「戻る」に統一**します。「キャンセル」という表記は使いません。「キャンセル」と「戻る」が混在すると、ユーザーは2つの違いを考えてしまいます。FG2 は BackNavigator で前の画面に戻る思想で統一されており、離脱は常に「戻る」一語で表します。

フォームを破棄して離れる場合（入力途中で戻るなど）も、ラベルは「戻る」です。破棄の確認が必要なときは、ラベルを変えるのではなく確認ダイアログ側で担保します（削除の二段構えと同じ考え方）。

戻る系の導線は「戻る」（直前の画面へ）と「最初に戻る」（起点の画面へ）の2つです。**どちらを出すか・出さないかの判断は BackNavigator に任せます。** 画面側で表示条件を書きません。「最初に戻る」は履歴が2階層以上あるとき（直前の画面と最初の画面が別になるとき）にだけ出ます。

これらが正しく動くには、**起点となるビューで `push_current` を呼んでおく**必要があります。各機能の一覧画面のビューに加え、キャンペーンや Person など、その機能の起点となる画面のビューでも `push_current` すること。履歴が積まれていないと「戻る」「最初に戻る」は出ません（詳しくは付録の BackNavigator を参照）。

フォーム下部に置く確定アクションの並びは、**左から「最初に戻る」「戻る」「新規保存（または修正）」の順**に統一します。離脱導線を左、確定アクションを右端に置くことで、押し終わりの主操作が一定の位置に来ます。

### 3.3 削除は二段構え — 入口は控えめ、最終実行だけ赤

削除には「削除しようとする入口」と「後戻りできない最終実行」の2段階があり、見た目を分けます。

**入口（一覧・詳細画面の削除ボタン）** は強調しません。破壊的操作は配置（右端への分離・3.1）で十分に区別できます。色でさらに赤く塗ると、画面の中で削除がいちばん目立ち、本来の主要操作より視線を奪います。入口は**トラッシュアイコン＋黒系の控えめな表示**（`app-btn-trash`）にし、右端に分離します。アイコンで目立たせず、位置の遠さで誤クリックを防ぐ、という二重のガードです。

**最終実行（confirm の後の、本当に消すボタン）** だけは `app-btn--danger`（赤）にします。後戻りできない一押しはここだけなので、赤はこの最終実行に集約します。confirm の形（ダイアログ・モーダル・確認画面のどれか）は画面の事情に応じてコード君の実装時判断としますが、「入口は控えめ／最終実行だけ赤」の原則は全画面で守ります。

なお「削除の前にアーカイブを必須にするか」といった削除フローそのものの仕様は、本ガイドラインの管轄ではありません（各モデルの業務仕様＝本編仕様書で定めます）。ここで定めるのは見た目だけです。

### 3.4 アーカイブ化はアーカイブアイコンで

論理削除（アーカイブ化）も、削除と同様にアイコンで表します。**アーカイブアイコン**（箱にしまう図）を使い、色は黄（`app-btn--warning`、3.6）のまま。削除（トラッシュ）とアーカイブ（箱）でアイコンの形が違うので、物理削除と論理削除を取り違えません。

### 3.5 編集への導線 — 見出しの横にアイコン

セクション単位の編集（例：「メール内容」を編集する）は、独立した大きなボタンを置くより、**セクション見出しの横に編集アイコン**を添える形をとれます。見出しと編集導線が同じ場所にあるので、「何を編集するのか」が直感的に分かり、画面のボタン数も減ります。

### 3.6 色 — 信号機メタファー

> 原則3 の具体化。色は意味です。割り当てを画面ごとに変えないでください。

| 操作の種類 | 意味 | クラス | 色 |
|---|---|---|---|
| 詳細・展開（▼） | 補助・閲覧 | `app-btn--outline-secondary` | グレー枠線・白背景 |
| 戻る・トグル OFF | 補助 | `app-btn--secondary` | グレー塗り |
| 編集 | 安全な操作 | `app-btn--success` | 緑 |
| 新規作成・トグル ON | 主要・前向き | `app-btn--primary` | 青 |
| マージ実行・マージ復元 | 注意（やり直せる） | `app-btn--warning` | 黄 |
| アーカイブ化・非アーカイブ化 | 注意（やり直せる） | `app-btn--warning` | 黄 |
| 削除（物理） | 危険（やり直せない） | `app-btn--danger` | 赤 |

**黄（やり直せる注意操作）の実体**：FG2 で黄に当たるのは、アーカイブ化／非アーカイブ化（タグ・カテゴリ・配信リスト・キャンペーン・テンプレート・Person の archived）と、**マージ実行・マージ復元**です。マージ実行は PersonMergeLog が undoable で残り後から復元でき、マージ復元はその取り消しそのものなので、いずれも「影響はあるが取り消せる」黄に属します。黄は単なるアーカイブ用ではなく、FG2 の業務中核操作を束ねる実体のあるカテゴリです。

**赤と黄で「入口」の扱いが違う**：赤（やり直せない＝物理削除）は二段構え（3.3）にし、入口をトラッシュ＋黒で目立たせず、最終実行だけ赤にします。一方、黄（やり直せる＝マージ・アーカイブ）は入口を隠しません。マージは業務フローで積極的に押す操作なので、黄で普通に見せます。「戻せないものだけ入口を隠す、戻せるものは隠さない」という区別です。

カラーコードは Bootstrap5 のデフォルト値を参考にしつつ、`app.css` の既存トーンに合わせます。

**適用範囲**：この色規約は FG2 全体の標準です。展開は一括ではなく段階的に行います。新規画面・これから手を入れる画面はこの規約に従い、既存画面（cards / contacts / persons など）は、その画面に触れる機会に合わせて順次揃えていきます。

### 3.7 アイコンの色は既定で黒

アイコンの色は、原則として**黒（黒系）を既定**とします。色は意味（3.6）に使う資源なので、アイコンを無造作に色付けすると意味の伝達が薄まります。アイコンは普段は黒で静かに置き、色をのせるのは個別に指定がある場合だけにします。

## 第4章 入力と選択

> 原則2（既存資産で完結）と原則4（説明は隠す）から導かれます。

### 4.1 チェックボックス・ラジオはトグルボタンに統一

選択肢の UI は、素の丸・四角のチェックではなく、押すと色が変わる**トグルボタンの見た目**で統一します。状態が一目で分かり、押せる範囲も広くなります。

実装は **Bootstrap の `.btn-check` ではなく、自前の `app-radio-toggle`**（`app.css`）を使います。仕組みは Bootstrap の `.btn-check` と同型で、ネイティブの `input` を視覚的に隠し、隣の `label` を `:checked` / `:has()` で着色するだけです。Bootstrap 本体を入れずに同じ見た目が得られます（理由は原則2）。

トグル化には2つの方式があります。どちらも `{{ field }}` の自動レンダリングに乗り、同じ `app-radio-toggle` の CSS を共有します。

- **choices override 型**：もともと複数の選択肢を持つフィールド（例：送信元方式）。フォームの `__init__` で選択肢ラベルを差し替える。
- **widget 差し替え型**：`BooleanField`（ON/OFF の2択）。`widget` を `RadioSelect` に差し替え、`(True, "適用する"), (False, "適用しない")` の2択にする。型は `BooleanField` のまま維持されるので、モデル側の検証ロジックに影響しません。

**例外**：検索フォームのチェックボックスや、テーブルの全選択チェックなど、トグルボタンが性質的に合わない箇所は無理に統一しません。

### 4.2 入力の制約はサーバ側バリデーションに任せる

「この方式のときはこの項目を変更できない」といった業務制約は、UI 側で先回りしてグレーアウトや自動チェック外しで潰さないでください。ユーザーが操作した結果は受け取り、不正ならサーバ側バリデーションでエラーを返します。UI で勝手に状態を書き換えると、ユーザーは「なぜ変わったのか」が分からず、かえって混乱します。制約の根拠（特定電子メール法など）はエラーメッセージで伝えます。

エラーを「どこで返すか」はここで定めますが、エラー文を「どう書くか」は第5章（5.2）で定めます。

### 4.3 補足説明はツールチップに

入力欄の補足は、欄の下に常時表示せず、ラベル横の「?」アイコン（`app-help-icon`）にまとめ、ホバーでツールチップ表示します（既存の floating-tooltip に乗ります）。これにより普段の画面はすっきり保たれ、説明が必要な時にその場で開けます（原則4）。

## 第5章 フィードバックと状態表示

> 原則5（操作には必ず応答を返す）から導かれます。

### 5.1 処理を受け付けたら、すぐ遷移して状態を見せる

時間のかかる処理（名刺取り込み・メール配信など）のボタンを押したら、**その場で待たせず、すぐに次の画面へ遷移**します。FG2 はフォーム送信を PRG（POST → Redirect → GET）で扱っているので、受付処理を済ませたら即リダイレクトし、遷移先の画面で「いま何が起きているか」を見せます。新しい仕組みは足さず、既存の PRG の延長で実現します。

遷移先で見せる状態は3つです。

- **受け付けた（処理中）**：「取り込みを受け付けました。処理中です」。裏で cron／バッチが動いていることをユーザーに伝え、押し直しを防ぎます。
- **完了した**：「取り込みが完了しました」「配信が完了しました」。
- **一部失敗した**：全部成功・全部失敗の二択にせず、「5件中4件を取り込みました。1件は読み取れませんでした」のように、成功と失敗の内訳を示します。

無反応の時間を作らないことが要点です。押した直後に画面が変われば、ユーザーは「効いた」と分かり、二重取り込み・二重送信が起きません。

### 5.2 エラーは「次の一手」まで書く

エラー文は「失敗した」で終わらせません。**何が起きたか**と、**次に何をすればいいか**の両方を、ユーザーの言葉で書きます。エラーを行き止まりにせず、次の行動へ橋を架けます。

FG2 で最も効くのは OCR 失敗時です。名刺が読み取れなかったとき、FG2 には手動で入力する経路があります。だから「読み取れませんでした」だけで止めず、「読み取れませんでした。手動で入力できます →」と、その場から次の経路へ案内します。失敗が袋小路にならず、ユーザーは作業を続けられます。

エラーをどこで返すか（サーバ側バリデーション）は 4.2 を参照してください。ここで定めるのは文面の書き方です。

### 5.3 空のときは「最初の一歩」を案内する

連絡先がまだ1件もない、配信リストが空、初めてログインした ―― こうした「まだ何もない」画面では、空っぽのテーブルをそのまま見せません。**「まだありません」と、次に何をすればいいか**を一緒に示します。

例：連絡先ゼロのとき「まだ連絡先がありません。名刺を取り込みましょう →」。配信リストが空のとき「配信リストがありません。新しく作成しましょう →」。

FG2 はこれからディストリビュータが新規に使い始めます。最初に開く空っぽの画面が「何をすればいいか分かる」かどうかは、製品の第一印象に直結します。空状態は、操作のついでではなく、最初の案内役だと考えてください。

## 第6章 コンポーネント参照（付録）

> 実装時に参照する具体物です。第1〜5章の原則・ルールを実現するための部品一覧。

### ボタン
- `app-btn` … 基底クラス。修飾子で色を付ける。
- 色修飾子 … `app-btn--primary`（青）/ `--secondary`（グレー塗り）/ `--outline-secondary`（グレー枠線）/ `--success`（緑）/ `--warning`（黄）/ `--danger`（赤）
- `app-btn-trash` … 削除の入口専用。トラッシュアイコン＋黒系・控えめ表示。一覧・詳細では右端に分離。
- 削除の最終実行（confirm 後）… `app-btn--danger`（赤）。後戻りできない一押しだけ赤にする。
- アーカイブ化 … アーカイブアイコン（箱）＋ `app-btn--warning`（黄）。
- マージ実行・マージ復元 … `app-btn--warning`（黄）。やり直せる操作なので入口は隠さない。
- 操作ボタンの並び … 主要群を左に、削除を右端に分離。
- アイコンの色 … 既定で黒。色をのせるのは個別指定がある場合のみ。

### 選択UI（トグル）
- `app-radio-toggle` … ラジオ／チェックをトグルボタン化する自前クラス。隠し input ＋ label を `:checked` / `:has()` で着色。
- choices override 型 … フォーム `__init__` で `choices` のラベルを差し替え。
- widget 差し替え型 … `BooleanField` の `widget` を `RadioSelect(choices=[(True,"適用する"),(False,"適用しない")])` に差し替え、`required=False`。

### 補足説明
- `app-help-icon` … ラベル横の「?」。ホバーでツールチップ。
- floating-tooltip … 既存のツールチップ表示の仕組み（app.js）。

### フィードバック表示
- 処理中・完了・一部失敗などの状態表示は、既存のメッセージ表示の仕組み（Django messages framework／既存の通知コンポーネント）に乗せる。新しい仕組みは作らない。
- 遷移は PRG（POST → Redirect → GET）。受付処理後に即リダイレクトし、遷移先で状態を見せる。
- 空状態は一覧テンプレートの「データ0件」分岐に、案内文＋次の一手リンクを置く。

### 折りたたみ
- `app-collapsible` … 折りたたみコンテナ。
- `app-collapsible__header` ＋ `data-action="toggle-collapsible"` … 開閉トリガー。初期状態は閉（`is-open` クラスなし）。

### 戻る導線（BackNavigator）
- `{% back_link back %}` … 「戻る」リンク（`<a>`）を返す。履歴が1階層以上（`back_exist`）あるときだけ。無ければ空。判定・URL・ラベルをすべてタグ内部に隠すので、テンプレートに `{% if %}` を書かない。
- `{% back_all_link back %}` … 「最初に戻る」リンク（`<a>`）を返す。履歴が**2階層以上**（`back_all_exist`＝直前と起点が別画面のとき）あるときだけ。無ければ空。ラベルは `back_all_title`（既定「最初に戻る」）。
- `{% append_back_url url back %}` … 次画面に back_stack を引き継ぐリンクに付ける。
- `{% hidden_back_field back %}` … POST フォーム用の hidden フィールドを生成。
- `{% back_url back %}` / `{% back_all_url back %}` … URL 文字列のみを返す特殊用途（JS・リダイレクト等）。画面に戻るボタンを置く通常用途では `back_link` / `back_all_link` を使う。
- 各機能の一覧・起点ビュー（キャンペーン、Person など、検索条件やページなどのクエリを持つ画面）で `push_current(title, keys)` を呼ぶ。これで履歴が積まれ、「戻る」「最初に戻る」が機能する。詳細・新規作成・編集など単独画面は `push_current` を呼ばず、`append_back_url` / `back_link` で戻りに乗る。
- フォーム下部の確定アクションは、左から「最初に戻る」「戻る」「新規保存（または修正）」の順に並べる（3.2）。
- 戻るボタンは画面右上に置く。縦に長い画面では、右下にも右寄せで補助的に置いてよい。

### レイアウト数値（目安）
- コンテンツのカード枠に `max-width` ＋ `margin: 0 auto` で中央寄せ。
- 編集フォーム … 狭め、`720〜800px` 目安。
- 詳細画面 … 広め。2カラムは `minmax(320px, 420px) 1fr` など。
