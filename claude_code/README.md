# claude_code/ ディレクトリ運用ガイド

**最終更新：** 2026-05-30
**対象読者：** FreeGroup2 プロジェクトに関わる全 AI（オーパス君、ジット君、コード君 A/B、クローム君、サブエージェント 4 担当）

---

## 1. このディレクトリの目的

`claude_code/` は **AI 向けの運用情報** を集約する場所である。

FreeGroup2 プロジェクトでは、設計判断・却下案・運用ルール・フェーズ別の作業文脈といった情報が、これまで個々の AI のチャット履歴やメモリに分散していた。チャットを跨ぐと文脈が失われ、同じ議論を繰り返したり、過去の決定を踏み外したりする事故が発生していた。

`claude_code/` を導入することで、**情報資産を個人（AI 個体）から組織（リポジトリ）に移行** する。AI が代替わりしても、リポジトリを読めばプロジェクトの判断履歴と現在の作業文脈が再構成できる状態を目指す。

---

## 2. ディレクトリ構造

```
claude_code/
├── README.md                         ← このファイル
├── decisions/                        ← プロジェクト横断の決定ログ
│   ├── INDEX.md                      ← 決定ログの索引
│   ├── TEMPLATE.md                   ← 個別決定ファイルのひな型
│   └── 2026-MM-DD_<議題名>.md        ← 個別決定ファイル
└── <バージョン>_<フェーズ名>/         ← フェーズ別作業文脈
    ├── CURRENT.md                    ← 現在進行中の状態
    └── archive/                      ← 過去スナップショット（節目で作成）
        └── CURRENT_2026-MM-DD.md
```

### 2.1 フェーズフォルダの命名規約

`<バージョン>_<フェーズ名>` の形式で統一する。

**例：**

- `1.6.0_OpenCV/`
- `1.6.0_mailing/`
- `1.7.0_OCR改善/`

**理由：**

- バージョン番号順に並ぶ（`ls` で時系列に把握できる）
- フェーズの帰属が一目で分かる
- ブランチが消えても文脈が残る（`claude_code/` の所有者はリポジトリであって、一時的なブランチではない）

**ブランチとの対応：** `CURRENT.md` の冒頭にブランチ名を明記する。

## 3. `docs/` との分離原則

| ディレクトリ    | 対象読者                  | 内容                                          |
| --------------- | ------------------------- | --------------------------------------------- |
| `docs/`         | 人間（開発者・ユーザー）  | ユーザーガイド、運用手順、UI ガイドライン等   |
| `claude_code/`  | AI                        | 作業文脈、決定根拠、却下案、運用ルール        |

**重複は陳腐化の元。** 両方に同じことを書かない。`docs/` は完成形を提示し、`claude_code/` は判断過程を残す。

---

## 4. `CURRENT.md` の役割

各フェーズフォルダ直下に置く、**そのフェーズの「いま」を 1 ファイルで把握できる文書**。

セッション開始時に AI（特にコード君 A/B とサブエージェント）が最初に読む想定。

### 更新タイミング

- フェーズ開始時：オーパス君がドラフト作成
- 節目（マイルストーン完了時・週次など）：更新提案
- セッション終了時：当日の進捗を反映
- セッション開始時：最終更新日が古かったらオーパス君が検知して更新提案

### 過去スナップショット

大きな節目で `archive/CURRENT_YYYY-MM-DD.md` として履歴を残す。`CURRENT.md` 本体は常に「現在」を表す。

---

## 5. `decisions/` の役割

プロジェクト横断の重要決定をファイル化する場所。フェーズフォルダではなく `claude_code/decisions/` に集約する（フェーズを跨いで参照されるため）。

### 5.1 判定基準（5 項目）

以下のいずれかに該当する決定はファイル化する：

1. **「やってはいけないこと」が含まれる決定**
2. **複数の選択肢から 1 つを選んだ決定**（却下理由も記録）
3. **設計の前提を変える決定**
4. **過去の決定を撤回・変更する決定**
5. **複数フェーズ・複数モジュールにまたがる決定**

該当しない決定（実装の細部、コーディングスタイルなど）はファイル化しない。`CURRENT.md` の進捗欄や、コミットメッセージで十分。

### 5.2 ファイル形式

- ファイル名：`YYYY-MM-DD_<議題名>.md`
- 個別ファイルのひな型：`TEMPLATE.md`（コピーして使う）
- 索引：`INDEX.md` で一覧管理

## 6. 誰がどこを読み書きするか

| 役割                            | 読む                                                              | 書く                                                              |
| ------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| **オーパス君**（設計の壁打ち）  | 全体                                                              | CURRENT.md ドラフト、decisions 草案、INDEX.md 更新案              |
| **ジット君**（仲介・整理）      | 全体                                                              | リポジトリへの実保存（オーパス君の草案をコミット可能な形にする） |
| **コード君 A/B**（実装）        | 該当フェーズの CURRENT.md、関連する decisions                     | CURRENT.md の進捗欄（指示があれば）                               |
| **クローム君**（UI 検証）       | 該当フェーズの CURRENT.md                                         | 通常は書かない                                                    |
| **サブエージェント 4 担当**     | 該当フェーズの CURRENT.md、関連する decisions（特にメタ視点担当） | 通常は書かない                                                    |

**原則：** 書き込みはオーパス君とジット君に集約する。コード君が `claude_code/` を書き換える運用にすると、実装と文書管理が混ざって事故る。

---

## 7. セッション開始時のチェックリスト（オーパス君向け）

新セッションが始まったら、オーパス君は以下を確認する：

1. たんたんから指示があったフェーズフォルダの `CURRENT.md` を読む
2. 最終更新日を確認し、**1 週間以上前なら更新提案** する
3. 関連する `decisions/` を確認する（CURRENT.md 内に参照リンクを書いておく運用）
4. たんたんに「いま何を優先したいか」を聞き、文脈を最新化する

---

## 8. 価値観（このディレクトリを運用する上での原則）

- **仕様書を盲信させない**：たんたんは何度も仕様書を 1 から書き直してきた。決定は固定ではなく見直し対象。
- **ユーザー視点・実運用視点で無駄を削ぐ**：実営業に効く機能セットに絞る、凝った設計より動くものを優先。
- **判断は人間の専権事項**：AI エージェントは検知・ストップ・報告に徹する。`claude_code/` は AI の判断材料を増やすが、最終判断はたんたんが下す。
- **オーパス君は対話パートナー＋ハブ＋文書化担当**：保管庫機能はリポジトリに移譲、対話と文書化に集中。
