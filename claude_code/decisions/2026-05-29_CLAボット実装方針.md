## 1. 確定事項

### 1.1 採用ツールと方式

CLA Assistant の **Action 版（lite 版）** を採用する。ホスト版（cla-assistant.io）は不採用。

却下理由（ホスト版）：署名記録を第三者サーバーに預けることになり、著作権移転型 CLA の証拠保全に不利。また前段ゲート（後述 1.4）を差し込めない。Action 版なら署名記録を自リポジトリ管理下に保全でき、ワークフロー YAML を自分で書けるため前段ゲートを挿入できる。

### 1.2 バージョン固定

`contributor-assistant/github-action` を**バージョン固定（`@v2.6.1` 系で pin）**して使う。当該リポジトリはアーカイブ済み（読み取り専用・今後の更新なし）だが、既存リリースは引き続き機能する。フォークへの追従はしない。

理由：FG2 の貢献者母数は小さく、CLA チェックは枯れた単純機能。フォーク追従の管理コストの方が割に合わない。

### 1.3 署名記録の保管先

CLA Assistant が自動生成する署名記録（`cla.json`）は、**本体リポジトリではなく別の private リポジトリ**に保管する。

理由：public な本体リポジトリに署名一覧を置かない。台帳系を公開リポジトリに置かない運用方針と一貫させる。

### 1.4 前段ゲート（FG2 独自ロジック）

CLA Assistant のステップの**前に自前の照合ステップを 1 つ挿入**する。動作は次のとおり。

- PR 作成者の GitHub ユーザー名を「登録アカウント一覧」（1.5）と照合する
- 一覧に**無い** → fail（登録外の貢献者として弾き、署名に進ませない）
- 一覧に**ある** → CLA Assistant のステップへ渡す

stock の `allowlist` 入力は「署名免除リスト（素通りさせる）」で意味が逆のため使わない。実際にマージを止める enforcement は、**main ブランチのブランチ保護で「CLA チェックの成功」を必須**にすることで実現する（fail だけではマージは止まらない）。

### 1.5 登録アカウント一覧（GitHub アカウント管理の正本）

別 private リポジトリに 1 ファイルとして持つ。1 行あたり次を持たせる。

- GitHub ユーザー名
- 紐づくディストリビュータ（FG2-NNNN）
- ICLA / CCLA の区分
- （CCLA の場合）締結日・CCLA バージョン・締結証拠ファイルへの参照

このファイルが、CCLA の「GitHub アカウント申告方式」（第9条）の実体であり、**GitHub アカウント管理の正本**となる。ディストリビュータ登録台帳（Google スプレッドシート）はディストリビュータ登録までを担い GitHub アカウントは持たない。GitHub アカウント管理はこの一覧に分離して一元化する（台帳にカラムを増やさない）。

前段ゲート（1.4）の判定材料と、割引計算（1.10）の土台を、この 1 ファイルで兼ねる。

### 1.6 ICLA / CCLA の出し分け

配管は**共通**にする。前段ゲートを通過した者は、ICLA・CCLA いずれも PR 内で署名コメントを取り、記録は `cla.json` に残す。違いは**署名文面のみ**。

- ICLA：個人が著作権移転に同意する文面
- CCLA：「自分は FG2-NNNN の CCLA 配下の所属者であり、本貢献が CCLA に基づき会社に帰属することを理解の上で署名する」旨の文面

却下案A：法人所属者に**個人 ICLA** を署名させる。→ 「個人が著作権移転」となり、CCLA（会社が移転）と矛盾するため却下。

却下案B：CCLA は前段ゲート通過で**素通り pass（署名なし）**。→ 個人・PR レベルの貢献痕跡が残らず、`cla.json` の記録が ICLA と非対称になる。割引区分の追跡にも不利なため却下。

### 1.7 CCLA 念押し署名の頻度

**初回 1 回**（CLA Assistant の標準動作。一度署名すれば以降の PR は自動 pass）。PR ごとの毎回署名は求めない。

理由：念押し署名は「自分は CCLA 配下だと理解した」という認識確認であり一度で足りる。権利移転の実体は会社の CCLA 締結（1.8）が担う。稀な貢献に毎回求めるのは過剰。

### 1.8 会社単位の CCLA 締結（契約本体）

CCLA の締結そのものは**ボットの外**で受理する。ディストリビュータ登録時または貢献申し出時に、`CLA-corporate.md` への同意と申告 GitHub アカウントの届出を受け、次の 2 つを残す。

- (A) 同意の証拠：会社から受け取った同意済み CCLA（PDF またはメール文面）を別 private リポジトリにファイル保管。会社名と CCLA バージョンがファイル名で分かるようにする
- (B) 申告内容：登録アカウント一覧（1.5）に対象アカウント群を CCLA 行として追加

`cla.json` には手を入れない（CLA Assistant の自動管理領域を手書きで壊さない）。CCLA の手動記録は `cla.json` と別ファイルに分ける。

ICLA と CCLA は記録の形式が異なる（ICLA＝PR 内署名による自動 JSON 記録／CCLA＝会社単位の手動証拠ファイル＋一覧行）が、保管場所は同じ別 private リポジトリに揃える。

### 1.9 改訂時の再署名

**CLA 文書（`CLA-individual.md` / `CLA-corporate.md`）そのものを改訂したときのみ**、署名ファイルの版（`signatures/versionN`）を上げて再署名を取る。

タリフ（割引率＝附則C・年間登録料＝附則B）の変更では CLA 再署名は求めない。これらは License 第15条の改訂手続きと、年次更新時にその時点の版が適用される仕組み（第5.2／第15.2）で回収する。

却下：タリフ変更でも再署名を求める。→ タリフは変更頻度が高く、重い操作（再署名）に結びつけると貢献体験が悪化するため却下。

### 1.10 割引区分の判定運用

- **マージ時**に、PR へ区分ラベルを貼ることを基本とする（例：`discount:feature` / `discount:bugfix` / `discount:doc` 等）。中身を理解しているマージの瞬間が最も正確
- **更新時**に、ジット君が当該ディストリビュータに紐づくアカウント（1.5 から引く）のマージ済み PR を当該年度で検索し、ラベル抜けをクロスチェックする。さらに区分案・附則C の割引率・累積後割引率（上限 80%）・年間登録料への適用後金額まで「下書き」として**算定（提案）**する
- **最終確定はたんたん**。License 第7.6条が区分判定をライセンサー裁量と定めるため、承認行為は人間が握る

ジット君：列挙＋要約＋区分案＋割引率＋適用後金額の算定（提案）まで。たんたん：それを見て確定（承認）。

## 2. 未決の運用ルール（実装着手時に詰める）

### 2.1 セキュリティ脆弱性報告（20%）の受付経路と記録

附則C の割引対象には PR 以外に「セキュリティ脆弱性報告」が含まれる。これは PR ではないため、更新時の `is:pr is:merged` 検索では拾えない。受理時に手動で記録（一覧または別記録）に書き込み、更新時にジット君が PR 検索結果と併せて参照する方針。受付経路と記録先の確定が未了。

### 2.2 割引が効く「年度」の定義

第7.4 は「マージされた年度の年間登録料に適用」、第5.3 は登録の有効期間を登録日から 1 年と定める。したがって割引年度は**暦年ではなく登録更新サイクル**。ジット君に検索期間を渡す際は「前回更新日〜今回更新日の 1 年」で切る、と定義を固める必要がある。

### 2.3 退会・登録解除時の一覧処理

退会フローに「紐づく GitHub アカウントを登録アカウント一覧から除外する」ステップを追加する（以後は前段ゲートで弾かれる）。あわせて第14.2 の解除後 180 日猶予期間との関係（猶予期間中の貢献可否）の整理が未了。

## 3. 実装の着手時期

最初の外部個人 PR が現れる、または見込みが立つまで**保留**とする。貢献者母数がほぼゼロの現時点で先回りして作る必然性は薄い、というコスト判断による。仕組みは本書で確定済みであり、貢献が来てから着手しても間に合う（最初の 1 件はボット無しの手動署名対応で足りる）。

## 4. 割り切ってよい点（これ以上詰めない）

- 前段ゲートの判定対象は PR 作成者（author）1 人で十分（共著 PR は母数ゼロのため考慮しない）
- ラベル付与はたんたんが行う
- `cla.json`（ボットの自動管理）と登録アカウント一覧（手動管理）の責務分担は「一覧＝誰が貢献可＋割引台帳／`cla.json`＝ボットが署名を記録」で固定
